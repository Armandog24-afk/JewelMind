# Thickness Function Model

## The real function

The Shank's radial thickness at longitudinal position `u` is:

```
t(u) = baseThicknessMm * taper_ratio(u, thicknessTaper)
```

where `baseThicknessMm` is `outer_radius(definition) - inner_radius(definition)` — the same quantity `geometry/constants.py::outer_radius()` derives from `definition.band.thickness` — and `taper_ratio()` is the identical pure function `taper.py` also uses for width (see [`548-taper-model.md`](548-taper-model.md)). This is the thickness term of `builder.py::_section_wire()`:

```python
thickness = (base_outer_r - inner_r) * taper_ratio(u, thickness_taper)
outer_r = inner_r + thickness
```

Note the important asymmetry with width: `inner_r` is **not** tapered. Every section, regardless of `u`, uses the same `inner_r = inner_radius(definition)` — the ring's finger-hole radius, which must stay constant all the way around for the ring to actually fit. Only `outer_r` moves, by adding the tapered `thickness` to the fixed `inner_r`. This is why `t(u)` is expressed as `base_outer_r - inner_r` (the base thickness) rather than as a taper on `outer_r` directly — tapering `outer_r` in isolation would not correctly express "how much metal thickness remains at this point," since `inner_r` is the fixed reference.

## Machine-readable contract

[`specs/shank/v1/thickness-function.schema.json`](../../../specs/shank/v1/thickness-function.schema.json) documents one sample of `t(u)` as `{baseMm, mode, bottomRatio, u, thicknessMm}`, with `thicknessMm = baseMm * taper_ratio(u, {mode, bottomRatio})`, always exactly `baseMm` at `u=0`/`u=1` regardless of `mode` — the same head-anchoring guarantee as width (SHANK-GOV-011).

## Real sample values

From `specs/shank/v1/test-vectors/thickness-function-vectors.json`, generated by actually running the code (`baseMm = 1.8`, the default `band.thickness`):

| `mode` | `bottomRatio` | `u` | `thicknessMm` |
|---|---|---|---|
| `NONE` | 1.0 | 0.0 | 1.8 |
| `NONE` | 1.0 | 0.5 | 1.8 |
| `NONE` | 1.0 | 1.0 | 1.8 |
| `TOWARD_BOTTOM` | 0.6 | 0.0 | 1.8 |
| `TOWARD_BOTTOM` | 0.6 | 0.5 | 1.08 |
| `TOWARD_BOTTOM` | 0.6 | 1.0 | 1.8 |

`1.8 * 0.6 = 1.08` — confirming `t(0.5) = baseMm * bottomRatio` at the bottom, matching the same formula shape as width.

## Where `thicknessSamplesMm` on generated metadata comes from

`builder.py::_build_tapered_shank()` computes the `TAPERED` metadata shape's `thicknessSamplesMm` field the same way:

```python
"thicknessSamplesMm": {
    "headMm": (base_outer_r - inner_r) * taper_ratio(0.0, thickness_taper),
    "bottomMm": (base_outer_r - inner_r) * taper_ratio(0.5, thickness_taper),
},
```

exactly `t(0)` and `t(0.5)`. As with `widthSamplesMm` (see [`546-width-function-model.md`](546-width-function-model.md)), these are CONSTRUCTION_PARAMETER values per SHANK-GOV-013 — computed from the same taper calculation that determined each section's actual `outer_r` during the loft, not independently re-measured from the finished solid.

## Interaction with width taper and profile

Width and thickness taper are independently controlled — `widthTaper` and `thicknessTaper` are two separate `BandTaperSpec` values on `BandSpec`, and `_section_wire()` applies both `taper_ratio()` calls independently within the same section (`combined_width_and_thickness_taper` in the capability registry, `status: "current"`). Neither taper affects which `profile_type` (`flat`/`comfort_fit`) is used — see [`545-section-profile-contract.md`](545-section-profile-contract.md); taper changes dimensions, never the cross-section's shape. And per SHANK-GOV-014, the tapered thickness path has one known limitation: because `outer_r` varies by angular position, there is no single "circle at radius X" to select for the outer-rim fillet the uniform path applies, so tapered shanks always report `filletApplied: false` with an explicit `filletSkippedReason` — this is unaffected by which of `widthTaper`/`thicknessTaper` (or both) triggered the tapered construction path.
