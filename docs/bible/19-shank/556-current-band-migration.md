# Current Band Migration

## The classification: MINOR, additive

`domain/schema.py::BandSpec` gained two new fields this Sprint, `widthTaper`/`thicknessTaper` (both `BandTaperSpec = Field(default_factory=BandTaperSpec)`, default `mode: "NONE"`). Per [`05-jdl/081-schema-versioning-and-migrations.md`](../05-jdl/081-schema-versioning-and-migrations.md)'s own PATCH/MINOR/MAJOR table, MINOR is defined as:

> An additive, backward-compatible change: a new optional field with a default, a new enum member appended to an existing list, a new semantic rule that only adds diagnostics (never changes acceptance of a previously-valid document from valid to invalid)

Both new fields fit this definition exactly: they are optional (each defaults via `default_factory`), and their default value (`mode: "NONE"`) reproduces bit-identical pre-Sprint-17 geometry, so no previously-valid document changes acceptance status. `schemaVersion` correctly stays `"0.1.0"` — this Sprint's change requires no bump per the same document's Migration Requirement 1, which reserves a `schemaVersion` bump for a MAJOR change only.

## The `definitionHash` drift, documented honestly

`definitionHash` is a SHA-256 hash of `canonical_json()`, which is built from `model_dump(mode="json")` — this includes every field, including newly-added fields at their default value. Once `BandSpec` gained `widthTaper`/`thicknessTaper`, every existing document, once re-validated and re-hashed by live code, produces a different `definitionHash` than it did before this Sprint — even though `mode: "NONE"` reproduces identical geometry.

This finding deliberately does not conflate itself with [`081-schema-versioning-and-migrations.md`](../05-jdl/081-schema-versioning-and-migrations.md)'s Migration Requirement 4:

> No migration may silently alter a `definitionHash` for a document whose `schemaVersion` field value is unchanged.

That rule concerns **migrating an already-stored old document** — taking a document saved under one schema version and transforming it, without changing its declared `schemaVersion`, into something that hashes differently. This Sprint did not do that: no stored document was migrated by any code path. What happened instead is **normalization-time default-filling on a freshly re-validated document**: any document run through `JewelryDefinition.model_validate()` today — new or old — gains the two new fields at their default value as part of ordinary validation, the same as it always has for every other field with a default. The practical symptom (a changed hash for logically-unchanged content) looks identical to what Migration Requirement 4 forbids, but the mechanism is different: there is no migration step involved, only the ordinary fact that an additive schema change adds fields to every freshly-validated document's canonical form. This distinction is recorded here explicitly rather than silently absorbed, per the Bible's standing rule against letting a real tension disappear into rewritten prose.

## Verified: Golden regression detection was unaffected

`geometry_quality.snapshot.compare_snapshot()` — the real Golden Suite regression comparator — was checked directly and confirmed to never read `definitionHash` anywhere in its comparison logic. All 9 pre-Sprint-17 Golden cases remained `STABLE` with zero baseline updates (see [`555-shank-golden-strategy.md`](555-shank-golden-strategy.md)), which is independent, practical confirmation that the hash drift has no bearing on regression detection.

## The largest practical ripple effect: Designer's `flatten_definition()` recursion bug

Before this Sprint, `designer/normalizer.py::flatten_definition()` flattened a `JewelryDefinition` into dotted-path scalar values only one level deep. It was not written to handle a nested object appearing under a top-level section field — a case that had simply never occurred before, since no `BandSpec` field (or any other section's field) had ever itself been a nested Pydantic object. Once `BandTaperSpec` was added as a nested object under `band` (`band.widthTaper`, `band.thicknessTaper`), this one-level flattening crashed on any definition containing it, because the flattener attempted to treat the nested `BandTaperSpec` dict as a scalar `FieldDiff` value.

The fix: `flatten_definition()` was rewritten to recurse via a new `_flatten_into(out, prefix, value)` helper, which walks into any `dict` value found at any depth and only records a leaf as a scalar once it stops being a dict — see `designer/normalizer.py` lines 151-171. This produces real dotted paths like `band.widthTaper.mode`/`band.widthTaper.bottomRatio` instead of crashing.

This single fix resolved 260 of the 266 test failures that appeared immediately after the additive `BandSpec` schema change — by far the largest single practical consequence of what was otherwise a purely additive, backward-compatible field addition. It is recorded here as the concrete illustration that "additive and backward-compatible" describes JDL acceptance semantics, not a guarantee that every downstream consumer of a `JewelryDefinition`'s shape was already written to tolerate a new nested object at an existing field path.
