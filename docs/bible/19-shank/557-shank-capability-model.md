# Shank Capability Model

## The single source of truth

`geometry/shank/capability.py::SHANK_CAPABILITIES` is the only place allowed to assert a Shank capability is `current` (SHANK-GOV-015). It is mirrored — never hand-duplicated — at [`specs/shank/v1/capability-registry.json`](../../../specs/shank/v1/capability-registry.json), generated by a one-off script (`backend/generate_shank_specs.py`, run once, not part of the shipped code or test suite) and re-validated by `backend/tests/test_shank_schemas.py`. No documentation, Designer capability list, or Studio copy may claim a capability this registry marks `planned`.

## The model: `ShankCapability`

```python
class ShankCapability(BaseModel):
    model_config = ConfigDict(extra="forbid")

    capability: str
    status: CapabilityStatus       # Literal["current", "planned"]
    jdlExposed: bool
    generatable: bool
    inspectable: bool
    description: str
```

Three independent boolean axes, each answering a different question about a named capability:

- **`jdlExposed`** — can a caller actually request this through the real JDL schema (`domain/schema.py`) today? For every entry in the current registry, `jdlExposed` and `generatable` move together — nothing is JDL-exposed without also being buildable, and nothing planned is JDL-exposed.
- **`generatable`** — does `build_shank()` actually produce geometry for this capability today?
- **`inspectable`** — does the resulting geometry get a real, meaningful inspection result (even if only the generic component-level facts described in [`553-shank-inspection-contract.md`](553-shank-inspection-contract.md))? For every `current` entry this Sprint, `inspectable` is `true` because the generic component inspection path (`COMPONENT_PRESENT`/`SOLID_COUNT`/`VOLUME`/`SHAPE_VALID`/`BOUNDING_BOX`) already covers any real `band` component regardless of which capability produced it — `inspectable` here does not imply a dedicated Shank-specific inspection fact exists (see [`553-shank-inspection-contract.md`](553-shank-inspection-contract.md) for that gap).

For every `planned` entry, all three booleans are `false`: a planned capability cannot be requested, built, or meaningfully inspected, by definition.

## CURRENT (6 capabilities)

| Capability | Description |
|---|---|
| `uniform_shank` | Constant width/thickness all the way around — the pre-Sprint-17 default. |
| `flat_profile` | Rectangular cross-section, optional outer-rim fillet (uniform shank only). |
| `comfort_fit_profile` | Shallow outward-bulging inner edge; optional outer-rim fillet (uniform shank only). |
| `width_taper_toward_bottom` | Full base width at the head, linearly tapering to `bottomRatio*base` at the bottom. |
| `thickness_taper_toward_bottom` | Full base thickness at the head, linearly tapering to `bottomRatio*base` at the bottom. |
| `combined_width_and_thickness_taper` | Width and thickness taper applied together, independently controlled. |

## PLANNED (11 capabilities)

| Capability | Description |
|---|---|
| `outer_rim_fillet_on_tapered_shank` | No single "circle at radius X" exists once the radius varies by angle; not yet implemented. |
| `taper_toward_head` | Would move the connection-interface anchor away from `u=0`; deliberately out of v1 scope. |
| `designer_taper_proposal` | Designer may not propose `widthTaper`/`thicknessTaper` this Sprint (not in `KNOWN_JDL_FIELD_PATHS`). |
| `studio_taper_editor` | No Studio UI control for taper this Sprint — JDL/API-only. |
| `split_shank` | Multiple rails — architecture reserves the concept, v1 builds exactly one rail. |
| `cathedral_shank` | Belongs primarily to shoulder/head integration, not a profile type. |
| `knife_edge_profile` | A third section-profile type; not implemented. |
| `euro_shank` | A modified centerline path; the current path is circular only. |
| `twisted_shank` | Not implemented. |
| `multi_rail_shank` | See `split_shank` — the general case of more than one rail. |
| `sculpted_shank` | Local, non-parametric sculpting; not implemented. |

All 17 capabilities and their exact descriptions above are taken verbatim from `specs/shank/v1/capability-registry.json`, which is the generated, current mirror of `geometry/shank/capability.py::SHANK_CAPABILITIES` — read that file directly for any future capability addition rather than this document, which will drift out of sync unless updated in the same change per SHANK-GOV-015.

## What this means for adjacent systems

Every one of the 11 planned capabilities is a real, named reservation for future work rather than an unaddressed idea with no place to attach it — `designer_taper_proposal` and `studio_taper_editor` in particular record, explicitly, that Designer and Studio integration for taper are deliberately deferred rather than accidentally missing (see [`12-designer/README.md`](../12-designer/README.md) and [`11-studio/README.md`](../11-studio/README.md) for those systems' own current-capability contracts, which this registry does not restate). Widening `SHANK_CAPABILITIES` to move any planned entry to `current` follows the same process as any other capability change in this Sprint's governance: an ADR for the capabilities `540-shank-governance.md`'s "When an ADR is required" section names explicitly (new profile type, new taper mode, new centerline path, multiple rails, replacing loft), and an RFC for anything reaching beyond what that document already reserves.
