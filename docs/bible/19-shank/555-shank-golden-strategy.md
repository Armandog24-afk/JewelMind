# Shank Golden Strategy

## The zero-regression guarantee for uniform shanks

SHANK-GOV-003 requires that uniform-shank geometry (no taper requested) never regress, and SHANK-GOV-009 requires new capabilities to be proven with new Golden cases, never by retrofitting old ones. Both are verified directly by the real `goldens/solitaire-v1/manifest.json`: all 9 pre-Sprint-17 cases — `SOL-001-default-solitaire` through `SOL-009-warning-only-large-stone-four-prong` — remain `status: "STABLE"` and required zero baseline updates from this Sprint. This is the practical proof that `_build_uniform_shank()` is genuinely byte-identical to the pre-Sprint-17 construction, not merely believed to be: if the revolve/fillet construction path had changed in any way that affected volume, bounding box, or component relationships, at least one of these 9 existing snapshots would have failed comparison in `compare_snapshot()` and required either a real fix or an explicit, reviewed baseline update — neither occurred.

## The 3 new taper cases

`goldens/solitaire-v1/manifest.json` now lists 12 total `goldenIds`, adding exactly three new, `STABLE` cases this Sprint:

- `SOL-010-width-taper-solitaire` — width taper, comfort_fit profile, `bottomRatio: 0.6`.
- `SOL-011-thickness-taper-solitaire` — thickness taper, comfort_fit profile, `bottomRatio: 0.5`.
- `SOL-012-combined-taper-solitaire` — both width and thickness taper together, flat profile, width `bottomRatio: 0.7` combined with thickness `bottomRatio: 0.6`.

Per SHANK-GOV-009, these were added as entirely new cases; no existing SOL-001 through SOL-009 case was altered to add taper coverage into it. Each is a real, schema-valid `JewelryDefinition` variation generated by actually calling `build_solitaire_ring()` → `inspect_model()`, matching the same generation-then-verification method the original 9 cases used (see [`17-geometry-quality/README.md`](../17-geometry-quality/README.md)'s "What was investigated, not invented" section) — never a hand-invented snapshot.

## Why `fullSuite` only, not `fastSuite`

`fastSuite` remains exactly `["SOL-001-default-solitaire", "SOL-002-four-prong-comfort-fit", "SOL-003-six-prong-flat"]` — unchanged by this Sprint. `fullSuite` gained all three new cases (`SOL-010`, `SOL-011`, `SOL-012`), bringing it to all 12 golden IDs.

`fastSuite` exists as a small, quick-iteration smoke set for everyday development — three cases chosen before this Sprint, covering the default configuration and two prong/profile variations, none involving taper. Taper introduces a materially more expensive construction path (a 48-section loft vs. a single revolve) and a new class of metadata (`widthSamplesMm`/`thicknessSamplesMm`, `filletSkippedReason`) worth verifying on every full regression pass rather than every fast iteration. Placing the taper cases in `fullSuite` follows the same selection principle `fastSuite`'s original three cases already embody — a minimal, fast, representative subset for quick checks, with full coverage reserved for `fullSuite` — rather than introducing a new selection rule for this Sprint specifically.

## `knownLimitations`: the missing outer-rim fillet

Every one of SOL-010/011/012 involves the tapered construction path, and the tapered path never applies the outer-rim fillet — `filletApplied: false` with an explicit `filletSkippedReason` string is always set (see [`551-shank-generation-pipeline.md`](551-shank-generation-pipeline.md)). Per SHANK-GOV-014, this is recorded as a real, documented limitation rather than a silent gap: each of these three Golden cases lists the missing tapered-shank outer-rim fillet under its `knownLimitations`, so a reviewer comparing a future candidate snapshot against these baselines is not left to rediscover, from a metadata diff alone, that the absence of a fillet on these three cases is expected rather than a regression.

## Coverage this Sprint deliberately did not add

No Golden case exists for any of the 11 `planned` capabilities in `geometry/shank/capability.py::SHANK_CAPABILITIES` — split shank, cathedral shank, knife-edge profile, Euro shank, twisted shank, multi-rail shank, sculpted shank, `taper_toward_head`, or the tapered-shank outer-rim fillet (see [`557-shank-capability-model.md`](557-shank-capability-model.md)). This follows directly from SHANK-GOV-009's framing: a Golden case exists to lock in real, generated behavior, and none of these capabilities generates anything today for a case to capture. Adding a Golden case for any of them is only meaningful once the corresponding capability actually moves from `planned` to `current`.

## What a Golden pass on these three cases actually proves, and does not

Per [`17-geometry-quality/README.md`](../17-geometry-quality/README.md), a `STABLE` status is a software regression reference — it proves the tapered construction produces the same volume, bounding box, component set, and connectivity facts today that it produced when the baseline was accepted, using the same `RELATIVE_COMPARISON_TOLERANCE`/`ABSOLUTE_COMPARISON_TOLERANCE_MM` tolerances as every other case. It does not imply professional or manufacturing approval of any taper configuration (`baselineStatus: STABLE` never implies `professional_validation: validated`, per [`17-geometry-quality/514-professional-validation-boundary.md`](../17-geometry-quality/514-professional-validation-boundary.md)), and it does not measure or assert anything about the missing outer-rim fillet beyond recording that its absence is expected for these three cases specifically.

## No baseline write path outside `accept`

The same `accept_candidate_baseline(...)` write path governs SOL-010/011/012 as governs every other Golden case — no code specific to Shank or taper was added to `geometry_quality/` that could write to a baseline outside that one explicit, human-invoked path. A future change to `SECTION_COUNT`, the taper interpolation formula, or the head-anchoring convention would cause these three cases (and only these three, since the uniform cases never exercise the tapered path) to fail comparison, requiring the same reviewed `geometry-quality accept --reason "..."` step as any other intentional geometry change — never an automatic update.

## Recording the acceptance

Per SHANK-GOV-009/[`17-geometry-quality/500-quality-governance.md`](../17-geometry-quality/500-quality-governance.md)'s QUALITY-GOV-018, every accepted baseline change requires an entry in [`golden-update-register.md`](../appendices/golden-update-register.md). As of this document's own `last_updated` date, that appendix does not yet list SOL-010/011/012 — this is recorded here explicitly as a real, outstanding documentation gap rather than silently assumed already done, and should be closed in the same change that next touches that appendix.
