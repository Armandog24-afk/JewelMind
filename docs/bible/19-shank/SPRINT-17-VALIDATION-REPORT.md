# Sprint 17 Validation Report — Band & Shank System v1

## Shank documents created

`README.md`, the full `540`–`559` numbered set (20 docs, matching the README's reading order exactly), this validation report, and 4 new appendices (`A110`–`A113`) — 26 documentation files in total, all cross-referenced and none left as a forward reference to a future Sprint.

## Machine-readable schemas created

6 under `specs/shank/v1/`: `shank-definition.schema.json`, `section-profile.schema.json`, `width-function.schema.json`, `thickness-function.schema.json`, `taper-definition.schema.json`, `connection-interface.schema.json` — plus a real `capability-registry.json`, 5 examples, and 6 test-vector files, all generated by running the real `geometry.shank.builder.build_shank()` code.

## JDL schema validated: yes

`domain/schema.py::BandSpec` gained `widthTaper`/`thicknessTaper` (both `BandTaperSpec`, default `mode: "NONE"`) — an additive, backward-compatible MINOR change. `schemaVersion` unchanged at `"0.1.0"`. `backend/tests/test_shank_schemas.py::test_all_schema_files_exist_and_are_valid_json_schema`/`test_all_examples_validate_against_shank_definition_schema` confirm all 6 schema files and all 5 examples validate.

## Capability registry validated: yes

`geometry/shank/capability.py::SHANK_CAPABILITIES` (17 entries: 6 `current`, 11 `planned`) matches `specs/shank/v1/capability-registry.json` byte-for-byte via `test_capability_registry_matches_the_real_capability_registry_live`; no `planned` capability is `generatable`/`jdlExposed` (`test_capability_registry_never_lists_a_planned_capability_as_generatable`, plus the equivalent assertion in `test_shank.py::TestShankCapabilityRegistry`).

## Band backward compatibility: yes

Any request with `widthTaper.mode == thicknessTaper.mode == "NONE"` dispatches to `_build_uniform_shank()` — the byte-identical pre-Sprint-17 `revolve()` construction, including the outer-rim fillet. Verified two ways: (1) `test_shank.py::TestUniformShankBackwardCompatibility::test_default_definition_produces_the_pre_sprint17_recorded_volume` asserts the exact recorded band volume (`250.99168317654699 mm3`) and combined metal volume (`341.44334316909976 mm3`); (2) all 9 pre-existing Golden cases (`SOL-001` through `SOL-009`) in `goldens/solitaire-v1/` required zero baseline updates.

## Taper generation modes verified: 3/3

Width-only, thickness-only, and combined width+thickness taper were each verified with real generated geometry (not merely schema acceptance): `TestWidthTaperGeneration`, `TestThicknessTaperGeneration`, `TestCombinedTaper` each confirm a single valid solid with strictly less volume than the equivalent uniform shank, and `TestWidthAndThicknessFunctions`/`TestTaperSymmetry` confirm `taper_ratio()` returns exactly `1.0` at the head, exactly `bottomRatio` at the bottom, and identical values at symmetric offsets from the head in either direction.

## Geometry Inspection: unaffected, generic-only (honest gap noted)

`geometry/inspection/` has no Shank-specific code path — a tapered `band` is inspected through the exact same generic `FactType` facts (`SHAPE_EXISTS`, `SHAPE_VALID`, `SOLID_COUNT`, `VOLUME`, `BOUNDING_BOX`, connectivity, stone/metal separation) as a uniform one. There is currently no dedicated per-`u` Shank `FactType` — `widthSamplesMm`/`thicknessSamplesMm` in `build_shank()`'s metadata are CONSTRUCTION_PARAMETER values computed from the same `taper_ratio()` function used to build the loft, never an independently re-measured MEASURED_GEOMETRY fact. This is documented as a real, honest gap in [`shank-inspection-fact-catalog.md`](../appendices/shank-inspection-fact-catalog.md), not silently implied to be covered.

## Head connectivity preserved: yes

`ShankConnectionInterface.topZMm` never moves for any taper configuration — verified by `TestHeadConnection::test_connection_interface_top_z_is_unchanged_by_width_taper`/`test_connection_interface_top_z_is_unchanged_by_thickness_taper` (equality against the uniform-shank interface), `test_band_metadata_exposes_the_same_connection_interface` (the `band` component's own metadata matches the independently computed interface), and `test_tapered_solitaire_head_remains_placeable_and_connected` (a full solitaire with combined taper stays fully connected, stone/metal separated, with a matching prong count via `inspect_model()`). This is guaranteed structurally by `TOWARD_BOTTOM` always anchoring the full base dimension exactly at `u=0` (SHANK-GOV-011) — no special-case code was ever needed in `prongs.py`/`basket.py`.

## StoneReference separation preserved: yes, unaffected

No code in `geometry/shank/` imports or references stone geometry — `build_shank()`/`profile.py`/`taper.py`/`builder.py` construct only the `band` solid. `test_shank.py::TestHeadConnection::test_tapered_solitaire_head_remains_placeable_and_connected` explicitly asserts `report.assemblyResult.stoneMetalSeparation.fusedIntoProductionMetal is False` for a tapered solitaire, confirming LAW-006/ATLAS-GOV-007 hold unchanged.

## Prong count variation tested: yes

`TestShankConnectivity::test_tapered_shank_stays_connected_across_supported_prong_counts` parametrizes `prong_count` over `[4, 6]` with a width-tapered shank, confirming full connectivity and a matching generated prong count at both. `TestParameterSweep` additionally sweeps `prong_count x profile x width_ratio x thickness_ratio` (36 representative combinations) checking for a finite, positive, single-solid, non-NaN/non-Inf volume at every combination.

## STEP export + roundtrip: pass, with one honestly-reported and resolved finding

`TestShankStepExport::test_tapered_shank_step_export_is_non_empty` confirms a real, non-empty `.step` file is written for a tapered solitaire. `test_tapered_shank_step_roundtrip_has_no_regressions` confirms `step_roundtrip_check()` returns zero findings at the shipped `SECTION_COUNT = 48`. During tuning, a ~0.26% STEP-roundtrip bounding-box discrepancy was observed once at `SECTION_COUNT = 72` — it was not reproducible after settling on `SECTION_COUNT = 48` and was retested across 4 distinct taper configurations with zero discrepancies. This finding is reported here rather than silently dropped, per the Bible's fundamental rule against hiding a contradiction.

## STL export: pass

`TestShankStlExport::test_tapered_shank_stl_export_is_non_empty` confirms a real, non-empty `.stl` file; `test_tapered_shank_stl_structure_has_no_regressions` confirms `stl_structure_check()` returns zero findings for a tapered solitaire.

## Vision preview: no frontend code changes needed

No Studio taper controls exist this Sprint (`studio_taper_editor: planned` in the capability registry), and none of Vision's own code (`ModelViewport.tsx`, `useComponentGeometries.ts`) needed to change: Vision parses whatever STL the backend generates generically — it has no code path that assumes uniform band geometry or reads a JDL dimension to build a `THREE.BufferGeometry` (VISION-GOV-001/002). A tapered `band`'s STL is therefore rendered automatically through the existing pipeline the moment the backend produces one.

## Real bugs found and fixed during this Sprint's own implementation: 3

1. **A genuine circular import**, found by placing an early version of `geometry/connection.py` inside `jewelmind/ring/` instead of `jewelmind/geometry/`. Since `jewelmind.ring` must depend on Atlas and never the reverse, this was a real Atlas/Ring layering violation, not just an import-ordering accident. Fixed by relocating the module to `jewelmind/geometry/connection.py`; verified fixed from multiple real import orders.
2. **Designer's `flatten_definition()` only flattened JDL one level deep**, crashing on the new nested `BandTaperSpec` object once `widthTaper`/`thicknessTaper` were added to `BandSpec`. Fixed via a recursive rewrite; resolved 260 of 266 test failures that appeared immediately after the additive schema change.
3. **A Pydantic `StrictModel`/`validate_assignment` gotcha**: 4 `TestInvalidTaper` tests initially failed because they mutated an already-constructed `JewelryDefinition` instance directly (plain attribute assignment) rather than calling `model_validate()` on a fresh dict — `StrictModel` does not set `validate_assignment=True`, so an invalid mutation silently succeeded instead of raising. Fixed by rewriting all 4 tests to construct via `JewelryDefinition.model_validate()`, the real path every JDL input actually goes through.

A STEP-roundtrip bounding-box discrepancy (~0.26%) was also observed once during `SECTION_COUNT` tuning at 72 sections — see the STEP export section above; not classified as a shipped bug since it did not reproduce at the shipped `SECTION_COUNT = 48` across 4 retested taper configurations.

## `definitionHash` drift: investigated, confirmed harmless to Golden regression, documented

Adding `widthTaper`/`thicknessTaper` to `BandSpec` changed `definition_hash()` for every existing document once regenerated, because the SHA-256 hash of `canonical_json()` includes all fields and defaults. Verified via direct inspection that `geometry_quality.snapshot.compare_snapshot()` never reads `definitionHash` — Golden Suite regression detection was completely unaffected by this drift. The following stored spec/test-fixture files with hardcoded old hash values were regenerated from live code (never hand-typed): `specs/jdl/v1/test-vectors/definition-hash-vectors.json`, `canonicalization-vectors.json`, `specs/designer/v1/examples/complete-solitaire-request.json`, `specs/geometry-inspection/v2/examples/default-solitaire-inspection.json`/`four-prong-inspection.json`, `specs/alchemist/v1/test-vectors/normalization-vectors.json`, `specs/atlas/v1/test-vectors/metadata-vectors.json`, `specs/conversation/v1/examples/create-and-refine.json`.

## Known limitations carried forward

- **Tapered outer-rim fillet is not implemented.** There is no single "circle at radius X" to select once the radius varies by angle; every tapered Golden case's `knownLimitations` records this explicitly, and `filletSkippedReason` is always set on tapered metadata (SHANK-GOV-014).
- **No per-`u` independent geometric re-measurement.** `widthSamplesMm`/`thicknessSamplesMm` are CONSTRUCTION_PARAMETER values from the same function that built the loft, not a second, independent measurement of the finished solid at that position — see [`shank-inspection-fact-catalog.md`](../appendices/shank-inspection-fact-catalog.md).
- **No variable-shank-aware Forge rule evaluation.** `JM-BAND-001`/`JM-BAND-002` (minimum band width/thickness) and related Forge rules evaluate against the base `band.width`/`band.thickness` values only; no rule currently evaluates the tapered bottom dimension (`bottomMm`) against a minimum-feature-size threshold.
- **No Designer or Studio UI for taper.** `designer_taper_proposal` and `studio_taper_editor` are both `planned` in the capability registry — taper is JDL/API-only this Sprint.
