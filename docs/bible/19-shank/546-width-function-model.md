# Width Function Model

## The real function

The Shank's width at longitudinal position `u` is:

```
w(u) = baseWidthMm * taper_ratio(u, widthTaper)
```

where `baseWidthMm` is the unmodified JDL `band.width` value, and `taper_ratio()` is `geometry/shank/taper.py`'s pure function of `u` and a `BandTaperSpec` (see [`548-taper-model.md`](548-taper-model.md) for its exact formula). This is not a separate function in the code — it is the width term of `builder.py::_section_wire()`:

```python
half_width = base_half_width * taper_ratio(u, width_taper)
```

(`base_half_width = definition.band.width / 2`; the wire is built from `half_width`, so the resulting section's full width is `2 * half_width = base_half_width * 2 * taper_ratio(u, width_taper) = baseWidthMm * taper_ratio(u, widthTaper)`, matching the formula above exactly.)

## Machine-readable contract

[`specs/shank/v1/width-function.schema.json`](../../../specs/shank/v1/width-function.schema.json) documents one sample of `w(u)` as `{baseMm, mode, bottomRatio, u, widthMm}`, where `widthMm = baseMm * taper_ratio(u, {mode, bottomRatio})`. The schema states explicitly that `widthMm` is always exactly `baseMm` at `u=0`/`u=1` regardless of `mode` — a direct consequence of `taper_ratio()` always returning `1.0` at the head (see [`548-taper-model.md`](548-taper-model.md)).

## Real sample values

From `specs/shank/v1/test-vectors/width-function-vectors.json`, generated by actually running the code (`baseMm = 2.4`, the default `band.width`):

| `mode` | `bottomRatio` | `u` | `widthMm` |
|---|---|---|---|
| `NONE` | 1.0 | 0.0 | 2.4 |
| `NONE` | 1.0 | 0.5 | 2.4 |
| `NONE` | 1.0 | 1.0 | 2.4 |
| `TOWARD_BOTTOM` | 0.6 | 0.0 | 2.4 |
| `TOWARD_BOTTOM` | 0.6 | 0.5 | 1.44 |
| `TOWARD_BOTTOM` | 0.6 | 1.0 | 2.4 |

`2.4 * 0.6 = 1.44` — confirming `w(0.5) = baseMm * bottomRatio` exactly at the bottom, and `w(0) = w(1) = baseMm` exactly at the head, matching [`548-taper-model.md`](548-taper-model.md)'s head-anchoring guarantee (SHANK-GOV-011).

## Where `widthSamplesMm` on generated metadata comes from

The `TAPERED` metadata shape's `widthSamplesMm` field (`{headMm, bottomMm}`) is computed the same way, directly in `builder.py::_build_tapered_shank()`:

```python
"widthSamplesMm": {
    "headMm": base_half_width * 2 * taper_ratio(0.0, width_taper),
    "bottomMm": base_half_width * 2 * taper_ratio(0.5, width_taper),
},
```

This is exactly `w(0)` and `w(0.5)` in the notation above. As stated in [`542-shank-domain-model.md`](542-shank-domain-model.md) and per SHANK-GOV-013, these are CONSTRUCTION_PARAMETER values — computed from the same `taper_ratio()` calls that determined each section wire's actual `half_width` during the loft — not an independently re-measured width of the resulting solid. A downstream reader that needs a truly measured width from the built geometry (rather than the construction input that produced it) must derive it from the solid itself.

## What is not modeled

`w(u)` is evaluated only at the discrete sample points `u = i / SECTION_COUNT` (48 sections; see [`544-shank-path-contract.md`](544-shank-path-contract.md)) for the tapered loft path, and the loft ruled between them; there is no continuous width function evaluated by the kernel the way `revolve()` provides continuous sweep for the uniform path. Between two adjacent sampled sections, the loft's actual width follows OpenCascade's ruled-loft interpolation between the two wires, not a re-evaluation of `w(u)` at intermediate `u`. `w(u)` itself is `NONE`/`TOWARD_BOTTOM` only — no other taper mode, and no non-linear width curve, exists in v1 (see [`548-taper-model.md`](548-taper-model.md) for the full taper-mode contract and what is PLANNED).
