# Appendix: Intersection Fact Catalog

Real pairwise intersection and distance facts for the default six-prong solitaire, generated by `jewelmind.geometry.inspection.inspect_intersection()`/`inspect_distance()` — see [`471-component-intersection-model.md`](../16-geometry-inspection/471-component-intersection-model.md) and [`472-component-distance-model.md`](../16-geometry-inspection/472-component-distance-model.md).

| Pair | Min. distance (mm) | Intersection status | Intersection volume (mm³) |
|---|---|---|---|
| band ↔ stone_reference | 0.9 | NO_INTERSECTION (skipped — broad-phase eliminated) | 0.0 |
| band ↔ prongs | 0.0 | INTERSECTS | 0.022 |
| band ↔ basket_support | 0.0 | INTERSECTS | 0.117 |
| stone_reference ↔ prongs | 0.0 | INTERSECTS | 2.101 |
| stone_reference ↔ basket_support | 0.0 | INTERSECTS | 3.619 |
| prongs ↔ basket_support | 0.0 | INTERSECTS | 22.238 |

## Reading this table correctly

- **band ↔ stone_reference is the only genuinely separated pair.** Its real minimum distance (0.9mm) already proves separation beyond `CONTACT_TOLERANCE_MM` (1e-6mm), so `should_skip_intersection()` skips the more expensive boolean-common call entirely for this pair — the `0.0` intersection volume is a broad-phase-derived, not independently measured, value for this one row.
- **Every other pair genuinely intersects with a real, independently measured positive volume.** This is by design — `EMBED_MM = 0.4` deliberately makes production components overlap for genuine 3D union, and the stone reference deliberately overlaps prongs/basket_support for a physically plausible grip. None of this is a defect.
- **A positive intersection volume between StoneReference and a production component is never evidence the stone was fused into production metal** — see [`474-stone-metal-separation-inspection.md`](../16-geometry-inspection/474-stone-metal-separation-inspection.md) for why that's a structural check, not a geometric-intersection check.
