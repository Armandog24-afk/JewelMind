# Forge Governance

This document extends [`00-foundation/000-bible-governance.md`](../00-foundation/000-bible-governance.md), [`04-jewelry-domain/040-domain-governance.md`](../04-jewelry-domain/040-domain-governance.md), and [`05-jdl/060-jdl-governance.md`](../05-jdl/060-jdl-governance.md) with rules specific to the rule *system* itself: how a rule is defined, classified, versioned, and (eventually) professionally validated.

## FORGE-GOV-001 through FORGE-GOV-015

| ID | Rule |
|---|---|
| **FORGE-GOV-001** | All jewelry-domain rules must have stable IDs. An ID, once published in [`forge-rule-catalog.md`](../appendices/forge-rule-catalog.md), is never reused for a different meaning. |
| **FORGE-GOV-002** | Every rule must declare provenance — see [`094-rule-provenance-model.md`](094-rule-provenance-model.md). `unknown` is a valid, honest provenance type; an absent provenance declaration is not. |
| **FORGE-GOV-003** | A numeric rule cannot be called a professional standard without validated provenance. A `provenanceType` of `prototype_heuristic`, `mathematical_constraint`, `geometry_engine_constraint`, or `implementation_necessity` can never coexist with `professionalValidationStatus: validated` for the same rule version. |
| **FORGE-GOV-004** | Frontend rules cannot exceed backend authority. `shared/validation/engine.ts` may only mirror a subset of `backend/jewelmind/validation/engine.py`'s rules; it must never enforce something the backend does not, and the backend's verdict always wins on disagreement (restates ADR-004). |
| **FORGE-GOV-005** | Geometry code cannot silently introduce jewelry-domain thresholds. A numeric jewelry-domain constant belongs in `validation/` with a rule ID, not hardcoded inside `geometry/components/*.py` — see [`111-domain-rule-gap-analysis.md`](111-domain-rule-gap-analysis.md) for where this boundary is honestly imperfect today. |
| **FORGE-GOV-006** | A rule must declare whether it blocks generation, export, or neither — see `blockingScope` in [`092-rule-anatomy.md`](092-rule-anatomy.md) and [`099-severity-and-blocking-semantics.md`](099-severity-and-blocking-semantics.md). |
| **FORGE-GOV-007** | Every change to rule semantics requires version-impact analysis per [`108-rule-versioning.md`](108-rule-versioning.md) — is this a PATCH, MINOR, or MAJOR change to the rule? |
| **FORGE-GOV-008** | Professional validation status must be explicit — every rule declares `not_required`, `preliminary`, `required`, or `validated`; there is no implicit default that means "probably fine." |
| **FORGE-GOV-009** | Candidate rules generated by AI remain non-authoritative until they pass the full process in [`103-professional-validation-lifecycle.md`](103-professional-validation-lifecycle.md) — see [`114-future-ai-assisted-rule-discovery.md`](114-future-ai-assisted-rule-discovery.md). |
| **FORGE-GOV-010** | Conflicting rules must not be silently merged. If two rules would produce different verdicts for the same field under different scopes, both are recorded and surfaced — see [`101-conflicts-precedence-and-resolution.md`](101-conflicts-precedence-and-resolution.md). |
| **FORGE-GOV-011** | A rule must be testable — every entry in [`forge-rule-catalog.md`](../appendices/forge-rule-catalog.md) must reference at least one test, per [`112-rule-testing-strategy.md`](112-rule-testing-strategy.md). |
| **FORGE-GOV-012** | A rule must reference the canonical field paths it evaluates (`targetFields` in [`092-rule-anatomy.md`](092-rule-anatomy.md)), so its blast radius is inspectable without reading its implementation. |
| **FORGE-GOV-013** | Every rule must declare its evaluation stage (`FORGE-0`..`FORGE-9`) — see [`096-rule-evaluation-pipeline.md`](096-rule-evaluation-pipeline.md). |
| **FORGE-GOV-014** | Every accepted rule change must update its tests and documentation in the same change — `current-rule-registry.json`, [`forge-rule-catalog.md`](../appendices/forge-rule-catalog.md), and the relevant test file together. |
| **FORGE-GOV-015** | Rules must not silently mutate user intent — a rule may report a `suggestedValue`, but only a future, explicitly-confirmed auto-fix (see [`102-suggestions-and-auto-fix-contract.md`](102-suggestions-and-auto-fix-contract.md)) may ever change a stored value, and never without an audit trail. |

## When an ADR is required

Moving validation authority between the frontend and backend; changing which severities block which scopes; introducing a rule-condition DSL that can execute arbitrary logic; changing the rule-versioning scheme; or any change that violates FORGE-GOV-001 through FORGE-GOV-015 without superseding this document first.

## When an RFC is required

Introducing a new rule *family* (e.g. a whole new manufacturing profile, a new professional-validation domain, or a rule category not in the 11 defined in [`093-rule-classification-model.md`](093-rule-classification-model.md)) — per [`04-jewelry-domain/056-domain-extension-strategy.md`](../04-jewelry-domain/056-domain-extension-strategy.md)'s workflow, extended here to rule families specifically. Adding a single new rule within an existing family and category does not require an RFC, only the standard code+docs+tests change described in FORGE-GOV-014.
