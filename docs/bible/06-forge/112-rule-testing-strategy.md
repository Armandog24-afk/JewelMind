# Rule Testing Strategy

## Test categories

| Category | Meaning | Current coverage |
|---|---|---|
| UNIT RULE TEST | Tests one rule function in isolation | CURRENT — `backend/tests/test_validation.py` covers all 16 `JM-*` rules |
| BOUNDARY TEST | Tests the exact threshold value (just above/below) | PARTIAL — some rules (e.g. `JM-BAND-002`'s two branches) are boundary-tested; not exhaustively documented as a distinct category before this Sprint |
| INVALID TYPE TEST | Tests that a wrong JSON type is rejected structurally | CURRENT — `backend/tests/test_schema.py`, `test_schema_safety.py`, `test_jdl_schema_examples.py` |
| PROPERTY TEST | Tests a property that should hold across many generated inputs (e.g. "hash is always identical for identical input") | CURRENT for hashing/determinism (`test_geometry.py::test_definition_hash_is_deterministic`); no property-based testing library (e.g. Hypothesis) is used anywhere in this codebase |
| REGRESSION TEST | Re-tests a previously-fixed defect | Implicit — no rule has ever needed a regression fix, so no dedicated regression test exists yet |
| CONFLICT TEST | Tests two rules that could disagree | Not applicable today — see [`101-conflicts-precedence-and-resolution.md`](101-conflicts-precedence-and-resolution.md); no two rules currently conflict |
| PROFILE TEST | Tests a manufacturing/material profile's rule set | PARTIAL — `JM-MANUFACTURING-001` is tested, but no `ManufacturingRuleProfile` object exists to test as a unit (see [`104-manufacturing-profile-rules.md`](104-manufacturing-profile-rules.md)) |
| PROVENANCE TEST | Confirms a rule's declared provenance matches its actual justification | NEW this Sprint — `backend/tests/test_forge_registry.py` confirms the registry's shape, though it does not yet assert provenance-type correctness beyond schema-enum validity |
| PROFESSIONAL VALIDATION TEST | Confirms a validated rule's record is complete | Not applicable today — zero validated rules exist |
| GEOMETRY-INTEGRATION TEST | Tests a rule's effect on actual generated geometry | CURRENT — `backend/tests/test_geometry.py` |

## Requirements

- **Positive cases**: every rule has at least one test proving it does *not* fire on a valid input (implicitly, via `default_definition()` producing zero results across every test in `test_validation.py`).
- **Negative cases**: every rule has at least one test proving it *does* fire on an invalid input — confirmed for all 16 `JM-*` rules in `test_validation.py`.
- **Exact boundaries**: confirmed for the two two-branch rules (`JM-BAND-002`, `JM-PRONG-002`) via this Sprint's `test_forge_registry.py::test_jm_rule_severities_match_live_validation_engine`.
- **Diagnostic IDs**: confirmed via `ruleId` assertions throughout `test_validation.py` and the new `test_jdl_schema_examples.py`/`test_forge_registry.py`.
- **Severity**: confirmed the same way.
- **Blocking behavior**: confirmed via `test_api.py::test_generate_invalid_definition_returns_422` and `has_errors()`-level unit tests.
- **Deterministic results**: confirmed via `test_geometry.py::test_definition_hash_is_deterministic` and the repeated-run vectors in `specs/forge/v1/test-vectors/evaluation-vectors.json`.

## Machine-readable vectors created this Sprint

`specs/forge/v1/test-vectors/evaluation-vectors.json` (multi-rule firing), `severity-vectors.json` (boundary/branch behavior for the two two-branch rules plus every other rule's fixed severity), `precedence-vectors.json` (honest absence of real conflicts), `provenance-vectors.json` (provenance type per rule). All four were generated by running the real implementation or by direct code inspection, not invented.

## Test gaps identified

1. No dedicated boundary-test file exists as a distinct artifact — boundary behavior is currently proven indirectly through `test_validation.py`'s existing cases plus this Sprint's new cross-check, not through an exhaustive boundary-value matrix.
2. No property-based testing exists anywhere in this codebase (a `hypothesis`-style fuzz test across the full parameter space has never been run).
3. No conflict test exists, because no conflict exists to test.
4. No professional-validation test exists, because no validated rule exists to test.
