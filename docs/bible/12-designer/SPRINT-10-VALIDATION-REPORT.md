## Live provider implemented

**Yes** (`AnthropicDesignerProvider`, `backend/jewelmind/designer/provider.py`) — complete, real code using forced tool-use structured output against the Anthropic Messages API, with full error mapping (timeout/API error/missing tool_use/schema violation). **Not live-verified**: this development environment has no `ANTHROPIC_API_KEY` configured, so no live call to a real LLM was made in this Sprint. This is stated plainly rather than worked around — see the README's "single most important finding."

## Fake provider implemented

**Yes** (`FakeDesignerProvider`, dataclass-based, dependency-injected directly in tests) — used by all 108 new backend tests. Never wired into `get_designer_provider()`'s runtime factory, so it can never be mistaken for a live AI response by a real user.

## Supported languages

Italian and English, via hand-authored synonym tables in `normalizer.py`. Canonical output enum values are identical regardless of input language (verified by the corpus's `MULTILINGUAL` category — 4 cases pairing equivalent IT/EN requests).

## Supported intent types

19 JDL dotted field paths (`capability.py::KNOWN_JDL_FIELD_PATHS`): project name; ring size/inner diameter/size system; band width/thickness/profile; stone diameter/depth/shape; setting prong count/prong diameter/prong height/basket height/type; material metal; manufacturing method; jewelry category/style. Non-mappable descriptive language (e.g. "delicate", "elegante") is preserved verbatim as unresolved intent, never converted into an invented dimension.

## Deterministic corpus cases

**62 natural-language corpus cases** (`backend/tests/test_designer_corpus.py`, 64 test functions including 2 meta-tests) across all 11 required categories (EXACT_SUPPORTED, SUPPORTED_SYNONYM, MULTI_FIELD, MODIFY_EXISTING, AMBIGUOUS, VAGUE, UNSUPPORTED, PARTIALLY_SUPPORTED, MALICIOUS, INVALID_NUMERIC, MULTILINGUAL — see [`../appendices/designer-test-case-catalog.md`](../appendices/designer-test-case-catalog.md) for the exact per-category count and examples), plus 2 meta-tests confirming coverage. All run against `FakeDesignerProvider` — zero live AI calls.

## Unsupported-feature cases

Covered by the `UNSUPPORTED`/`PARTIALLY_SUPPORTED` corpus categories (10 cases) plus 3 dedicated unit tests in `test_designer.py`, exercising both provider-flagged unsupported features (halo, trilogy, pavé, bezel, necklace) and the deterministic capability backstop (an unsupported enum value like `stone.shape: "oval"` is caught even if a provider never flags it as unsupported).

## Ambiguity cases

Covered by the `AMBIGUOUS` corpus category (5 cases) plus 2 dedicated unit tests, exercising both the deterministic `AMBIGUOUS_METAL_TERMS` check (bare "gold"/"oro") and provider-reported ambiguities.

## Proposal-review workflow status

**Implemented and verified.** `DesignerPanel` shows "You asked" / "JewelMind understood" (with per-field provenance labels) / "Not yet mapped to a technical parameter" / "A few questions" (clickable clarification options) / "Not currently supported" / a Forge summary line, then "Apply proposal" / "Cancel". `currentDefinition` is never mutated before Apply. **Known, deliberate simplification**: the original brief's mockup showed three buttons ([Apply proposal] [Edit] [Cancel]); this implementation ships two, because `ConfigurationPanel` is always visible and editable both before and after applying — there is no separate "edit mode" to enter, so a third button would duplicate existing functionality. Documented in [`310-user-review-and-acceptance.md`](310-user-review-and-acceptance.md) and listed in [`321-designer-gap-analysis.md`](321-designer-gap-analysis.md).

## Modify-existing workflow status

**Implemented and verified.** `interactionMode: MODIFY` starts from `currentJDL` and only patches fields the request actually names; every unspecified field is preserved exactly (verified by `TestModifyProposalAndPreservation` in `test_designer.py` and 6 `MODIFY_EXISTING` corpus cases).

## Hallucinated-field rejection status

**Verified, structurally guaranteed.** Any field path outside the 19 known paths is dropped with a `DESIGNER_CAPABILITY_MISMATCH` diagnostic before it can reach a candidate JDL (`test_unknown_field_from_provider_is_rejected_not_smuggled_into_jdl`); any enum value outside the real capability set becomes an `UnsupportedFeature`, never a smuggled value (`test_unsupported_stone_shape_value_is_caught_deterministically`). This holds regardless of what a provider (real or fake) returns — the enforcement is in `capability.py`/`service.py`, not in provider honesty.

## Prompt-injection protections

A denylist-based `detect_prompt_injection_risk()` screens every request's text before it reaches any provider, rejecting it with `DESIGNER_SECURITY_REJECTED` (400). Covered by 6 `MALICIOUS` corpus cases plus 3 dedicated unit tests. Documented honestly as a coarse first layer, not a claim of complete immunity — see [`314-prompt-injection-and-untrusted-input.md`](314-prompt-injection-and-untrusted-input.md).

## External API calls required by CI

**No.** Every one of the 108 new backend tests and 4 new frontend tests uses `FakeDesignerProvider` or a mocked `interpretDesignRequest`; none requires `ANTHROPIC_API_KEY` or any network access.

With no `ANTHROPIC_API_KEY` configured (the real state of this environment): `DesignerPanel` rendered correctly above `ConfigurationPanel`; submitting a request produced a real `POST /api/designer/interpret` -> `503 DESIGNER_PROVIDER_UNAVAILABLE` (confirmed via network inspection); the UI correctly showed "AI interpretation is unavailable in this environment..."; the manual parameter editor (metal select, prong count, band profile, etc.) remained fully functional, confirmed by changing the metal select via a live DOM event and observing the value change. **Not verified live**: an actual successful AI interpretation — no live LLM call was made in this Sprint, for the reason stated above.
