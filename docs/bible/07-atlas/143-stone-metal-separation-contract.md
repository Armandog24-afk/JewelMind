# Stone-Metal Separation Contract

Formalizing LAW-006 at the Atlas level: **StoneReference may appear in preview; may appear in technical metadata; is not production metal; must be excluded from production exports by default; must not accidentally be fused into production geometry.**

## How current code enforces each clause

| Clause | Enforcement |
|---|---|
| May appear in preview | `write_component_previews()` iterates every entry in `GeneratedModel.components`, including `stone_reference` — no special-casing excludes it |
| May appear in technical metadata | `build_specification()` (`exporters/specification.py`) includes stone dimensions/volume in the generated text |
| Is not production metal | `stone_reference` is never passed to `_fuse_metal()` — only `band`, `basket`, `prongs` are |
| Excluded from production exports by default | `export_step()`/`export_stl()` both default `include_stone: bool = False`; `api/schemas.py`'s `includeStoneReference: bool = False` matches |
| Must not accidentally be fused | `_fuse_metal(band, prongs, basket)`'s signature does not accept a stone argument at all — there is no code path by which `stone_reference.shape` could reach the fuse call, not merely a runtime check that happens to prevent it |

## Machine-readable inspection vectors

`specs/atlas/v1/test-vectors/inspection-vectors.json` includes `atlas-test-stone-separation` (status `PASS`, checkType `CONNECTIVITY`): `stone_reference.bounding_box.zmin (11.5999999) >= band.bounding_box.zmax (10.7000000) - 1e-6`, generated by running `test_geometry.py::test_stone_reference_is_valid_and_separate_from_metal`'s exact assertion against the real default definition.

## What this contract does not currently check

No runtime or test-time check confirms **zero geometric intersection volume** between `stone_reference` and `combined_metal` — the current test only confirms the stone's bounding box sits entirely above the band's bounding box, which is a stronger-than-necessary but not exhaustive proof of non-intersection (two shapes with non-overlapping bounding boxes on one axis cannot intersect, so the current check is actually sufficient for the current geometry, but would not catch a future component whose bounding boxes overlap on that axis while the solids themselves still don't intersect, or vice versa). This is recorded as a gap (`ATLAS-GAP-006` in [`150-atlas-gap-analysis.md`](150-atlas-gap-analysis.md)), not silently assumed comprehensive.

**Sprint 14 update — and an important nuance this revealed**: [`16-geometry-inspection/`](../16-geometry-inspection/README.md) now measures the REAL pairwise intersection volume between `stone_reference` and every production component. The real finding is **not** "zero intersection" — `stone_reference` genuinely intersects `prongs` (2.10 mm³) and `basket_support` (3.62 mm³) on the real default solitaire, by design (the `EMBED_MM`-driven grip realism the prong/basket builders already used). Only `stone_reference` ↔ `band` measures zero intersection (0.9mm real minimum distance). This means "zero intersection volume" was never the right invariant to check in the first place — the actual, correct invariant this Sprint's `StoneMetalSeparationResult.fusedIntoProductionMetal` checks instead is **structural**: whether the stone's shape was ever an argument to `_fuse_metal()` (it never is, verified by the same function-signature argument made below), not whether it happens to occupy the same 3D space as a production component. See [`16-geometry-inspection/474-stone-metal-separation-inspection.md`](../16-geometry-inspection/474-stone-metal-separation-inspection.md) for the full treatment of this distinction.

## Structural guarantee, not just a runtime check

Because `_fuse_metal()`'s function signature never accepts a stone argument, stone-metal fusion is prevented by **the shape of the code itself**, not merely by a value that happens to be `False` today. This is a stronger guarantee than a boolean flag check would provide, and is worth stating explicitly as the reason LAW-006 has never been violated in this codebase's history.
