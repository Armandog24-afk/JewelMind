# Current Solitaire Golden Suite

The real Golden Suite lives under [`goldens/solitaire-v1/`](../../../goldens/solitaire-v1/) at the repository root, driven by [`goldens/solitaire-v1/manifest.json`](../../../goldens/solitaire-v1/manifest.json). It has exactly 9 cases, all `baselineStatus: STABLE`, all generated by the one-off `backend/generate_golden_fixtures.py` script (deleted before the final Sprint 15 commit — same discipline as Sprint 14's `generate_inspection_specs.py`) and independently reverified against their own saved baselines before being accepted.

Every case shares `expectedComponents: [band, basket_support, prongs, stone_reference]`, `assembly.componentCount: 4`, `assembly.productionComponentCount: 3`, `assembly.referenceComponentCount: 1` — the solitaire's component set does not change across any of the 9 variations, only dimensions/counts within it.

## SOL-009: `PASS_WITH_KNOWN_LIMITATIONS`, not a defect

`SOL-009-warning-only-large-stone-four-prong` is the one case whose `knownLimitations` is non-empty:

> "Triggers Forge warning JM-PRONG-003 (PRONG_COUNT_VS_STONE_SIZE); this is expected and does not indicate a geometry defect."

`harness.py::verify_golden()` checks `golden.knownLimitations` after severity classification: when `diff.severity` is `NONE` (i.e. the geometry matches the accepted baseline exactly) but `knownLimitations` is non-empty, the result status is `PASS_WITH_KNOWN_LIMITATIONS` rather than plain `PASS`. This means SOL-009's geometry itself is unchanged and matches its baseline — the "known limitation" is a Forge-domain observation (JM-PRONG-003 is a real, currently-registered rule; see [`06-forge/110-current-rule-inventory.md`](../06-forge/110-current-rule-inventory.md)) recorded alongside the golden, not a comparison outcome. A `REGRESSION_DETECTED`/`VERSION_REVIEW_REQUIRED` status still takes priority over `knownLimitations` in `verify_golden()`'s status logic — a known-limitation golden is not exempt from real regression detection.

## `fastSuite` vs. `fullSuite`

Both are real arrays in `manifest.json`, verified directly:

- **`fastSuite`** (3 cases): `SOL-001-default-solitaire`, `SOL-002-four-prong-comfort-fit`, `SOL-003-six-prong-flat`.
- **`fullSuite`** (9 cases): all 9 listed above, in the same order as `goldenIds`.

Neither `fastSuite` nor `fullSuite` is currently read by any code path in `backend/jewelmind/geometry_quality/` — `harness.py::verify_all_goldens()` calls `list_golden_ids()`, which reads `goldenIds` (all 9), not `fastSuite`/`fullSuite`. The split exists in the manifest today purely as declared data for a future targeted-vs-full workflow; see [`512-ci-regression-gating.md`](512-ci-regression-gating.md) for why no such workflow was needed this Sprint.
