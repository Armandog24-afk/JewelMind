# ADR-011: a real axis tilt on the arrangement instance transform

## Status

Accepted (Sprint 26).

## Context

`InstanceTransform` accepted a translation and **one** rotation, about the
vertical axis only. Its own docstring stated that as a decision rather than an
omission, on two grounds — both correct at the time:

1. `StoneSpec.orientation` already spins a stone about its own vertical axis, so
   a second such rotation would overlap it.
2. Tilt and roll were recorded as PLANNED in
   `arrangement/capability.py::full_3d_instance_orientation`, because
   "accepting a rotation no builder can execute would be a silently ignored
   field" (ARRANGE-GOV-011).

Sprint 26 needed a pavé on the shank's outer surface. That surface is
cylindrical about the finger axis, and its normal points radially outward, so a
stone set into it must lean by its own angular position. A stone left upright on
the flank of a shank does not sit on the shank — it passes through it. Placing
the field only where the normal happens to be vertical would confine a shank
pavé to the crest, which is one or two stones.

## Decision

Add two fields to `InstanceTransform`:

- `tiltDeg` — how far the instance's own axis leans away from `+Z`;
- `tiltAzimuthDeg` — the direction it leans toward, as an azimuth in the XY
  plane.

Two angles rather than one, because a tilt without a direction is not a
placement: a stone on the left of a band and one on the right lean by the same
amount in opposite directions. Together with the existing `rotationDeg` these
are ZXZ Euler angles, so the transform now expresses a complete orientation
rather than a partial one.

Both default to `0.0`, which is the identity.

**The field follows the capability, not the reverse.** It is accepted only
because `geometry/stone/instance.py::_tilted_about_own_center()` executes it —
a real kernel rotation about a horizontal axis through the solid's own centre.
ARRANGE-GOV-011 is honoured, not overridden: the rule forbids a field no builder
can execute, and there is now a builder.

## Consequences

- `full_3d_instance_orientation` moves from PLANNED to a real capability, with
  the precise statement of what it is: axis orientation plus own-axis spin,
  which is complete, and no separate "roll" concept because a roll about the
  instance's own axis IS `rotationDeg`.
- Order of operations is fixed and not interchangeable: scale, spin, tilt,
  translate. Spinning before tilting is what makes the two angles ZXZ Euler
  angles; tilting first would make the spin happen about an already-tilted axis,
  so the same two numbers would describe different placements depending on which
  ran first. Stated in the placer's own comments.
- Normalization folds `tiltAzimuthDeg` to `0.0` whenever `tiltDeg` is zero, so
  an upright instance has exactly one canonical representation. Without that,
  two identical upright placements differing only in a meaningless azimuth would
  produce different canonical JSON and different fingerprints.
- `tiltDeg` is rounded like a coordinate rather than folded like an angle,
  because it is a signed lean within `[-180, 180]`: folding `-30` to `330` would
  make an upward lean read as a downward one.
- Every pre-Sprint-26 document carries `0.0` for both, takes the identity path
  in the placer, and its solids are returned untouched. All 49 Golden baselines
  hold with no update, which is the evidence rather than the intention.
- `definitionHash` changes for every document, because two additive fields
  change canonical JSON. Every derived mirror was regenerated by running the
  real implementation, as Sprints 21–25 each did.

## Alternatives considered

**A full 3×3 orientation matrix.** Rejected: nine numbers with six constraints,
no canonical form, and no way to normalize for hashing. The two-angle form has
exactly one representation per orientation once the azimuth is folded.

**A category-specific "band angle" field.** Rejected: the arrangement layer is
category-neutral, and a field named for the shank would be meaningless for a
pendant or an earring. The azimuth formulation carries the same information
without naming an axis.

**Confining the pavé to surfaces whose normal is vertical.** Rejected as a
capability, not as an implementation: it would ship a shank pavé that is one
stone wide and call it a shank pavé.
