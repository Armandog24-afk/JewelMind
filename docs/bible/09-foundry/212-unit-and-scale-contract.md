# Unit and Scale Contract

## STEP declares its unit explicitly — confirmed by direct inspection

A real exported STEP file's `GLOBAL_UNIT_ASSIGNED_CONTEXT` entity reads:

```
#3539 = ( LENGTH_UNIT() NAMED_UNIT(*) SI_UNIT(.MILLI.,.METRE.) );
#3540 = ( NAMED_UNIT(*) PLANE_ANGLE_UNIT() SI_UNIT($,.RADIAN.) );
#3541 = ( NAMED_UNIT(*) SI_UNIT($,.STERADIAN.) SOLID_ANGLE_UNIT() );
```

Length is explicitly millimetres, consistent with JewelMind's own internal contract (LAW-007, "Use millimeters everywhere"). This confirms, by inspection rather than assumption, that STEP's declared unit and JewelMind's internal unit agree — the first time this specific fact has been directly verified in the Bible.

## Incidental finding: an embedded uncertainty value

The same unit context carries `UNCERTAINTY_MEASURE_WITH_UNIT(LENGTH_MEASURE(5.E-06), #3539, ...)` — 5×10⁻⁶ in the file's own millimetre unit, i.e. 5 nanometres. This is OpenCascade's own default STEP-translator uncertainty value, discovered incidentally while inspecting the unit declaration, not something JewelMind sets or relies on. See [`197-step-export-contract.md`](197-step-export-contract.md) and [`07-atlas/136-tolerance-model.md`](../07-atlas/136-tolerance-model.md) for the full context — this value must never be read as a statement about upstream geometric accuracy.

## STL declares no unit at all

The binary STL format specification has no field anywhere for a unit declaration. JewelMind's STL header is a free-text OpenCascade export banner (`"STL Exported by Open CASCADE Technology [dev.opencascade.org]"`, zero-padded to 80 bytes), confirmed by reading a real exported file's header bytes during this Sprint — not a unit marker. A number in a JewelMind STL file is millimetres only because this documentation, and the rest of the system's internal contract, says so; the file itself carries no evidence of it.

## Consequence for downstream consumers

A STEP consumer can, in principle, verify the unit programmatically by reading the file's own unit entity. An STL consumer cannot — it must be told the unit out of band. This is a real, format-inherent asymmetry between the two artifact types, not a JewelMind implementation gap; see [`211-stl-interoperability-boundaries.md`](211-stl-interoperability-boundaries.md) for the practical risk this creates (a slicer defaulting to the wrong unit).
