# Conversation Summary Model

## The shape

`ConversationSummary` (`backend/jewelmind/conversation/schemas.py`) is a flat Pydantic model with exactly five list-of-string fields, each defaulting to empty:

```python
class ConversationSummary(ConversationModel):
    acceptedDecisions: list[str] = Field(default_factory=list)
    intentThemes: list[str] = Field(default_factory=list)
    unresolvedQuestions: list[str] = Field(default_factory=list)
    rejectedDirections: list[str] = Field(default_factory=list)
    unsupportedDiscussed: list[str] = Field(default_factory=list)
```

`ConversationSession.summary` carries one live instance, updated incrementally as accepted changes and unsupported features occur (`_handle_accept()`, `_resolve_designer_proposal()` in `service.py`), and `context.py::compact_summary()` derives a (possibly extended) copy of the same shape when history is compacted — see [`388-history-compaction-model.md`](388-history-compaction-model.md) for exactly which turn fields feed which of the five lists.

## Deterministic Python, never an LLM call

`compact_summary()` is ordinary Python control flow over `session.turns` — a set of `if`/`for` statements checking real structured turn fields (`turn.accepted`, `turn.technicalChanges`, `turn.interpretedAction`, `turn.clarification.status`, `turn.unsupportedFeatures`) and appending to plain lists. It makes no provider call, no network call, and imports nothing from `jewelmind.designer.provider`. The docstring at the top of `context.py` states this directly: `ConversationSummary` is "always built from real structured turn fields — never generated by an LLM."

This is a direct implementation of the Sprint 12 brief's instruction to "prefer deterministic summary generation from structured events; do not require LLM summarization." JewelMind never asks a provider to read a transcript and produce prose — every summary field is either a literal field a turn already carried (a JDL path, a rejected turn's own `sourceText`, a feature name, a clarification question) or a straightforward transformation of one (`f"{s.target}.{s.concept}"` for intent statements, computed at proposal-resolution time in `service.py`, not inside `compact_summary()` itself).

## Consequences of determinism

- **Reproducibility.** The same session, compacted twice, produces byte-identical `ConversationSummary` output — there is no sampling, temperature, or provider-version variance to account for.
- **No summarization quality metric needed.** Because nothing is generated (only filtered/re-listed), there is no "did the summary lose meaning" failure mode to evaluate the way an LLM-produced summary would need — only the mechanical question of whether the field-mapping rules in [`388-history-compaction-model.md`](388-history-compaction-model.md) are correct, which `test_conversation.py::TestContext` exercises directly.
- **No cost or latency.** Compaction runs in-process, in the same call as everything else in `process_turn()` — no additional provider round-trip.

## What this model is not

It is not a natural-language digest a human would read as a paragraph — each list entry is a raw structured token (a JDL dotted path like `"material.metal"`, a raw source-text string, a feature name), not prose. Rendering a `ConversationSummary` into readable prose for a human, if ever needed, would be a presentation-layer concern; no such renderer exists in `frontend/src/components/ConversationPanel.tsx` today (it displays turns and proposals directly, not the summary object — see [`403-current-code-mapping.md`](403-current-code-mapping.md)).
