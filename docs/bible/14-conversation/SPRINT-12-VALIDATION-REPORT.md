# Sprint 12 Validation Report

## Documents created

`docs/bible/14-conversation/README.md` plus `370-conversation-governance.md` (20 CONV-GOV rules), 34 further numbered documents (`371`-`404`), plus this report — 37 files total. 8 new appendices: `conversation-action-catalog.md`, `conversation-state-catalog.md`, `conversation-reference-catalog.md`, `clarification-type-catalog.md`, `conversation-diagnostic-catalog.md`, `conversation-test-case-catalog.md`, `conversation-code-mapping.md`, `conversation-test-matrix.md` (`JM-BIBLE-A73` through `A80`, continuing from Sprint 11's last appendix, `A72`).

## Schemas created

9 JSON Schemas (Draft 2020-12): `conversation-action`, `clarification-thread`, `clarification-answer`, `conversation-state`, `turn-context`, `conversation-turn`, `conversation-summary`, `conversation-session`, `conversation-result`. 7 examples (one real generated flow per required scenario) and 7 test-vector files in `specs/conversation/v1/`, all generated by actually running the real `ConversationEngine` and its supporting modules — never hand-invented.

## Real multi-turn interaction implemented

**Yes** — `backend/jewelmind/conversation/service.py::ConversationEngine.process_turn()` accepts a client-carried `ConversationSession` on every request, appends the new turn, and returns the updated session for the next call to carry forward. The backend is stateless per request, exactly mirroring Designer's Sprint 10 architecture: no server-side persistence exists or is required.

## Clarification threads implemented

**Yes** — `ClarificationThread` (4 `ExpectedAnswerType` values), `clarifications.py::open_clarification()`, opened both from ambiguous-reference detection (`references.py::resolve_implicit_target()`) and from Designer's own `clarificationQuestions`.

## Clarification answer resolution implemented

**Yes** — `clarifications.py::try_resolve_answer()` validates NUMERIC/ENUM_CHOICE/CONFIRMATION/FREE_TEXT answers; `service.py::_handle_answer_clarification()` resolves only the one open thread it was opened for (CONV-GOV-007), rejecting an invalid answer without silently guessing.

## Proposal correction implemented

**Yes** — a turn arriving while a proposal is `ACTIVE` and not matching accept/reject phrasing classifies as `MODIFY_DESIGN_PROPOSAL`; `_handle_designer_routed()` supersedes the prior proposal (`status = "SUPERSEDED"`) before creating the new one — verified by CASE F (`TestCaseF_CorrectionSupersedesWithoutIntermediateMutation`), which confirms no intermediate six-prong mutation occurs before the four-prong correction is accepted.

## Proposal rejection/cancellation implemented

**Yes** — `_handle_reject()` (clears `activeProposal`, no state history touched) and `_handle_cancel()` (the general "undo" safety valve, checked first in `classify_action()`, clears both `pendingClarification` and `activeProposal` unconditionally).

## Stale-proposal protection implemented

**Yes** — `state.is_proposal_stale()` compares a proposal's `baseDefinitionHash`/`baseIntentHash` (captured at creation time) against fresh `definition_hash()`/`intent_hash()` of the caller's current values on every accept attempt; `_handle_accept()` raises `ConversationStaleContextError` (409) rather than applying a potentially-outdated candidate. No merge/rebase logic exists — a deliberate, documented choice ([`402-stale-context-and-concurrent-editing.md`](402-stale-context-and-concurrent-editing.md)) favoring conservative rejection over an unproven automatic merge.

## Reference-resolution targets supported

**10** — `RING`, `BAND`, `STONE`, `SETTING`, `PRONGS`, `BASKET`, `MATERIAL_APPEARANCE`, `OVERALL_PROPORTION`, `VISUAL_HIERARCHY`, `JEWELRY_PRODUCT` (`service.py::_KNOWN_TARGETS`), reusing Design Intent's own `TARGET_SYNONYMS` vocabulary rather than a second word list.

## Intent-only turns preserve current geometry

**Yes** — `_resolve_designer_proposal()` only calls the frontend's `applyDesignerProposal()` path when `proposal.diff.some(d => d.changed)` is true; verified by CASE B (`TestCaseB_IntentOnlyNeverStalesGeometry`) and the real `intent-only-refinement.json` example.

## Unspecified JDL values preserved across modifications

**Yes** — Conversation never authors its own JDL patch; every `MODIFY`-routed turn goes through the real `DesignerService.interpret()`, whose `_apply_patch()` overwrites only the field paths present in the resolved patch. Verified live by `specs/conversation/v1/test-vectors/preservation-vectors.json` and CASE A / CASE D (`TestCaseA_TechnicalModifyPreservesUnrelatedFields`, `TestCaseD_PreserveStoneWhileChangingMaterial`).

## Unsupported features preserved explicitly

**Yes** — a turn producing only unsupported features (no proposed fields) classifies as `REPORT_UNSUPPORTED`, adds each feature to `session.summary.unsupportedDiscussed`, and never creates a mutating proposal — verified by CASE E (`TestCaseE_UnsupportedThenAbandoned`).

## Conversation history used as design authority

**No** — `ConversationSession` never carries a copy of `JewelryDefinition` or `DesignIntent`, only content hashes (`currentJDLHash`/`currentIntentHash`) recomputed fresh from the caller's actual values on every request (`state.refresh_hashes()`). If a prior turn's text implies one value but the caller's current accepted JDL says another, the accepted JDL always wins (CONV-GOV-004/008).

## Live provider required by CI

**No** — every automated test (`test_conversation.py`, `test_conversation_engine.py`, `test_conversation_api.py`, `test_conversation_corpus.py`, `test_conversation_schemas.py`, `ConversationPanel.test.tsx`, `useConversationStore.test.ts`) uses `FakeDesignerProvider` or a mocked `interpretConversationTurn` exclusively — no test imports or calls `AnthropicDesignerProvider`.

## Deterministic conversation test cases

**80** real multi-turn cases in `backend/tests/test_conversation_corpus.py` (matching the "at least 80" target exactly), spanning all 17 required categories (`CREATE_THEN_MODIFY`, `TECHNICAL_MODIFICATION`, `INTENT_ONLY_MODIFICATION`, `REFERENCE_TO_PREVIOUS_COMPONENT`, `PRONOUN_RESOLUTION`, `AMBIGUOUS_REFERENCE`, `CLARIFICATION`, `CLARIFICATION_CORRECTION`, `PROPOSAL_REJECTION`, `PROPOSAL_CORRECTION`, `PRESERVE_UNSPECIFIED`, `UNSUPPORTED_FEATURE`, `PARTIAL_SUPPORT`, `STALE_CONTEXT`, `MALICIOUS_HISTORY`, `ITALIAN`, `ENGLISH`), plus 2 meta-tests confirming coverage. Separately, `backend/tests/test_conversation_engine.py` holds 15 integration tests, including the 6 REQUIRED CASE A-F scenarios from the Sprint 12 brief's section 40.

## Hallucinated state changes remaining

**0** — audited across every code path in `backend/jewelmind/conversation/`; every technical change traces to a real `DesignerProposal.diff` entry, every intent change to a real `designIntent.statements` entry, both computed exclusively by Designer's existing pipeline — Conversation never generates a change from prose.

## Unauthorized state mutations remaining

**0** — no code path applies a proposal's `candidateJDL`/`designIntent` without an explicit `ACCEPT_PROPOSAL` turn, and the backend itself never mutates a stored design (it is stateless per request); the frontend's own apply path (`ConversationPanel.tsx::handleAccept()`) only fires after the backend confirms `interpretedAction === "ACCEPT_PROPOSAL" && accepted === true`.
