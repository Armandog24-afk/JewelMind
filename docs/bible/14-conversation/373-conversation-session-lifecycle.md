# Conversation Session Lifecycle

This document is cited directly by `backend/jewelmind/api/routes.py::conversation_turn_route()`'s docstring and by `specs/conversation/v1/conversation-state.schema.json`.

## The session is entirely client-carried

There is no server-side session store. A session is created by `state.new_session(current_jdl, current_intent, now)` the first time a caller sends a `ConversationTurnRequest` with `session: null`; every subsequent turn sends the previous `ConversationResult.session` back as `ConversationTurnRequest.session`. `ConversationEngine` never keeps a session in memory between calls and never writes one to a database — see [`371-conversation-architecture.md`](371-conversation-architecture.md)'s "Stateless-per-request architecture" section.

## The 7 `SessionStatus` values

```
ACTIVE | WAITING_FOR_CLARIFICATION | PROPOSAL_READY | WAITING_FOR_ACCEPTANCE | IDLE | CLOSED | FAILED
```

A grep of `backend/jewelmind/conversation/service.py` and `state.py` for every `session.status =` assignment and `status=` constructor argument finds exactly four values ever actually written:

| Value | Where it's set | Meaning |
|---|---|---|
| `IDLE` | `state.new_session()` (initial); `_handle_reject()`; `_handle_cancel()` | No open clarification, no active proposal. |
| `ACTIVE` | `state.new_session()`'s counterpart in `_handle_accept()`; also set after a `REPORT_UNSUPPORTED` turn in `_resolve_designer_proposal()` | A turn was processed and the session is available for the next one, with no pending review item. |
| `WAITING_FOR_CLARIFICATION` | `_handle_designer_routed()` on an ambiguous reference; `_resolve_designer_proposal()` on a Designer-issued clarification question | A `ClarificationThread` is open. |
| `PROPOSAL_READY` | `_resolve_designer_proposal()` when a proposal (not a clarification, not a pure-unsupported report) is produced | An `activeProposal` is set and awaits accept/reject/correction. |

`WAITING_FOR_ACCEPTANCE`, `CLOSED`, and `FAILED` are declared in the `SessionStatus` type alias and validated by `conversation-state.schema.json`, but **no code path in the current implementation ever sets them**. This is an honest, documented gap, not a claim to walk back later without noticing it:

- `WAITING_FOR_ACCEPTANCE` looks, by name, as though it should be a distinct state between `PROPOSAL_READY` and acceptance — but the real state machine uses `PROPOSAL_READY` for that entire span and never introduces a second status for it.
- `CLOSED` would presumably represent a session the user or caller explicitly ended — there is no "close session" action among the 13 `ConversationActionType` values, so nothing can reach it.
- `FAILED` would presumably represent a session that failed unrecoverably — but every failure mode in this Sprint (invalid state, stale context, no pending clarification, provider failure) raises an `AppError` that aborts the HTTP request before any `ConversationResult` (and therefore any session with that status) is ever returned; the caller's last-known-good session is simply reused on retry.

## Real observed transitions

`specs/conversation/v1/test-vectors/state-transition-vectors.json` was generated by actually running `ConversationEngine.process_turn()` and recording `session.status` before/after each call — not hand-invented. Six real transitions across three scenarios:

| Scenario | From | To | Trigger | `sourceText` |
|---|---|---|---|---|
| create_then_accept | `IDLE` | `PROPOSAL_READY` | `MODIFY_DESIGN_PROPOSAL` | "Fammi un solitario in oro rosa con sei griffe." |
| create_then_accept | `PROPOSAL_READY` | `ACTIVE` | `ACCEPT_PROPOSAL` | "ok" |
| propose_then_reject | `IDLE` | `PROPOSAL_READY` | `MODIFY_DESIGN_PROPOSAL` | "Usa il platino." |
| propose_then_reject | `PROPOSAL_READY` | `IDLE` | `REJECT_PROPOSAL` | "no" |
| clarification_then_cancel | `IDLE` | `WAITING_FOR_CLARIFICATION` | `REQUEST_CLARIFICATION` | "Allarga la fascia." |
| clarification_then_cancel | `WAITING_FOR_CLARIFICATION` | `WAITING_FOR_CLARIFICATION` | `ANSWER_CLARIFICATION` | "annulla" |

The last row is worth reading carefully: the trigger is `ANSWER_CLARIFICATION`, not `CANCEL_INTERACTION`, because the text `"annulla"` was offered to the open clarification thread first (`classify_action()`'s `has_clarification` branch always wins over any other classification — see [`382-clarification-answer-resolution.md`](382-clarification-answer-resolution.md)), and `try_resolve_answer()` rejected it as an invalid answer for whatever `ExpectedAnswerType` was open, leaving the session in the same `WAITING_FOR_CLARIFICATION` state rather than actually cancelling. A real `undo`/`annulla l'ultima`/`revert` phrase is intercepted earlier, before the clarification check, by `classify_action()`'s `_UNDO_MARKERS` guard — see [`376-conversation-state-machine.md`](376-conversation-state-machine.md) for that specific edge.

## Session creation

`state.new_session()` sets `currentJDLHash`/`currentIntentHash` from the caller's initial `currentJDL`/`currentDesignIntent`, an empty `turns` list, `pendingClarification=None`, `activeProposal=None`, an empty `acceptedChangeHistory`, `lastReferencedTarget=None`, a fresh empty `ConversationSummary()`, and `status="IDLE"`. `createdAt`/`updatedAt` are both set to the same `now` timestamp on creation.
