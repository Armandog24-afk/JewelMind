# Stone Dimension Model

## The three canonical dimensions

| Name | Meaning | Local axis |
|---|---|---|
| **LENGTH** | Major horizontal dimension | Y |
| **WIDTH** | Minor horizontal dimension | X |
| **DEPTH** | Vertical dimension | Z |

Axis assignment is documented in full in [`565-stone-coordinate-and-orientation.md`](565-stone-coordinate-and-orientation.md); this document covers *which fields exist* and *how they resolve*.

"Major" and "minor" are naming conventions describing the intended role, not enforced constraints. Nothing rejects `length < width`; the geometry builds correctly either way (it simply produces a shape elongated along X instead of Y). No Forge rule judges the length/width ratio — a proportion judgement would be a professional threshold, and Stone System contains none (STONE-GOV-010).

## Two shape groups, two public field sets

### ROUND

```json
{ "shape": "round", "diameter": 6.5, "depth": 4.0 }
```

`diameter` and `depth`, exactly as before Sprint 18. This is the entire reason `diameter` still exists as a field: **backward compatibility** (STONE-GOV-016). Every pre-Sprint-18 stored document, every existing example, and every existing Golden case uses this form and continues to validate and generate byte-identically.

### ELONGATED and ANGULAR (every other shape)

```json
{ "shape": "oval", "length": 8.0, "width": 6.0, "depth": 4.0 }
```

`length`, `width`, and `depth`. `diameter` is meaningless for these shapes and is never read.

## Why round is not forced to expose length/width publicly

The brief's guidance was explicit on this point, and the implementation follows it: *"Do not force ROUND to expose fake independent length/width unless internal normalization benefits from it. Internal normalized representation may resolve round: length = diameter, width = diameter. But preserve public compatibility."*

So the split is:

- **Publicly**, round keeps `diameter`. Asking a caller to write `length: 6.5, width: 6.5` for a circle would be redundant and would break every existing document.
- **Internally**, round resolves to `length == width == diameter`, so no downstream module needs a shape special case to read a horizontal dimension.

This is the STONE-GOV-005 separation made concrete: shape and dimensions are distinct concepts, and the *public field shape* is allowed to differ from the *resolved geometric contract*.

## The resolution layer

`backend/jewelmind/domain/stone_dimensions.py` is the single reconciliation point:

```python
def resolved_length_mm(stone: StoneSpec) -> float:
    if stone.shape == "round":
        return stone.diameter        # asserted non-None by StoneSpec's own validator
    return stone.length

def resolved_width_mm(stone: StoneSpec) -> float:
    if stone.shape == "round":
        return stone.diameter
    return stone.width

def resolved_depth_mm(stone: StoneSpec) -> float:
    return stone.depth               # identical field for every shape
```

Three properties matter:

1. **It is the only place the shape/dimension mapping lives.** New code must read dimensions through these functions, never `stone.diameter` directly (STONE-GOV-005). A direct `stone.diameter` read in new code is a latent crash for any non-round stone, since the field is `None` there.
2. **It lives in `domain/`, not `geometry/` or `validation/`.** Both Atlas geometry and Forge validation consume it; placing it in either would have created a new cross-layer coupling. See [`561-stone-architecture-overview.md`](561-stone-architecture-overview.md).
3. **The asserts are honest.** They document that `StoneSpec`'s own `@model_validator` has already guaranteed the field is present — the resolution functions do not re-validate, and they do not silently substitute a default if it is missing.

Real resolved values are recorded per shape in `specs/stone/v1/test-vectors/dimension-vectors.json`, generated by running these functions, and re-verified live by `test_stone_schemas.py::test_dimension_vectors_match_live_resolution`.

## Who consumes resolved dimensions

| Consumer | Use |
|---|---|
| `geometry/stone/builder.py` | Half-extents for the outline; depth split into crown/pavilion. |
| `geometry/constants.py::prong_center_radius()` | `resolved_width_mm() / 2` as the girdle reference for provisional prong placement — placement geometry, **not** a threshold. See [`573-stone-setting-interface.md`](573-stone-setting-interface.md). |
| `validation/engine.py::_stone_rules()` | `min(resolved_length, resolved_width)` as the real minimum horizontal extent for `JM-STONE-002`. |
| `shared/validation/engine.ts` | The identical mirror of the above (FORGE-GOV-004). |

## Required-dimension enforcement

Two layers, deliberately:

- **Structural / semantic (authoritative):** `StoneSpec`'s `@model_validator(mode="after")` requires `diameter` for round and **both** `length` and `width` otherwise, raising a real `ValidationError`. Mirrored in `shared/types/jewelry-definition.ts::isValidStone()`.
- **JSON Schema (`specs/jdl/v1/jdl.schema.json`):** widens the types (`["number", "null"]`) and the `shape` enum, but deliberately does **not** encode the conditional requirement as an `if`/`then`. Per [`../05-jdl/075-validation-pipeline.md`](../05-jdl/075-validation-pipeline.md), a conditional business requirement belongs to the semantic layer, not the structural one.

A shape's required dimensions are also declared declaratively in `geometry/stone/capability.py` as `requiredDimensions`, and mirrored into `specs/stone/v1/shape-registry.json`.

## What is not a dimension

`orientation` is not a dimension — it is a placement property, documented in [`565-stone-coordinate-and-orientation.md`](565-stone-coordinate-and-orientation.md). Carat weight, spread, and any other commercial descriptor do not exist as fields and must never be inferred from dimensions.
