# Stone / Setting Compatibility v2

The machine-readable matrix is
[`specs/stone/v2/setting-compatibility-v2.json`](../../../specs/stone/v2/setting-compatibility-v2.json),
generated from `jewelmind/stone/capability.py::compatibility_matrix_v2()`.

## The three statuses

| Status | Means |
|---|---|
| `SUPPORTED_SOFTWARE` | Exercised end to end; the setting's geometry suits this outline |
| `EXPERIMENTAL` | Real geometry builds, but placement is not shape-optimized |
| `UNSUPPORTED` | Refused explicitly, with a structured error |

**None means professionally validated.** Every combination is `NOT_REVIEWED`
(STONEV2-GOV-007).

## Current matrix

| Stone | Prong | Bezel |
|---|---|---|
| round | `SUPPORTED_SOFTWARE` | `SUPPORTED_SOFTWARE` |
| oval | `EXPERIMENTAL` | `SUPPORTED_SOFTWARE` |
| custom | `EXPERIMENTAL` | `SUPPORTED_SOFTWARE` |
| pear, emerald, cushion, princess, marquise | `EXPERIMENTAL` | `EXPERIMENTAL` |
| heart, radiant, asscher, trillion, baguette, tapered_baguette, triangle, trapezoid, lozenge, hexagon, kite, shield, half_moon | `EXPERIMENTAL` | `EXPERIMENTAL` |
| pearl | `UNSUPPORTED` | `UNSUPPORTED` |
| imported | `UNSUPPORTED` | `UNSUPPORTED` |

`custom` at `SUPPORTED_SOFTWARE` for bezel is the sprint's headline result: the
bezel consumes the normalized outline contract directly, so a stone with no
named cut needs no bezel code of its own.

## Why declaration and behaviour cannot drift

`specs/stone/v2/test-vectors/setting-compatibility-vectors.json` is generated by
**actually attempting every combination**. Each row records the declared status
alongside what really happened — the components produced, or the refusal code.

The generator asserts the correspondence: an `UNSUPPORTED` row must carry a
refusal code, and a `SUPPORTED`/`EXPERIMENTAL` row must have produced real
components. All 42 rows agree, and the only refusals are pearl × prong and
pearl × bezel.

That is stronger than a hand-maintained table, which can only be wrong quietly.

## Why the Setting registry no longer lists shapes by hand

Sprint 19's `setting/capability.py` hard-coded the seven Stone v1 shapes into
`stoneShapesSupported`/`Experimental`/`Unsupported`. Sprint 20 immediately
proved why that is a drift hazard: fourteen new shapes plus `custom` appeared,
and a bezel over a custom outline was **refused as "not supported"** even though
the geometry pipeline built it correctly.

The split is now DERIVED from the Stone System registry by
`_stone_shapes_by_compatibility()`. Stone remains the authority on what a shape
IS; Setting remains the authority on what it can DO with one. A new shape cannot
be forgotten in the Setting registry because the Setting registry no longer
lists shapes.

## Why `EXPERIMENTAL` is the honest status for thirteen new cuts

`OUTLINE_CARDINAL` placement puts prongs at the outline's cardinal extremes,
found by a support function over the sampled outline. That is genuinely
shape-aware — it follows the real silhouette — and it is genuinely not
shape-optimized:

| Shape | What a jeweller would do that JewelMind does not |
|---|---|
| heart | Place a prong at the cleft or avoid it deliberately |
| kite, shield, lozenge | Grip the tips |
| trillion, triangle | Grip the three corners |
| baguette, tapered_baguette, trapezoid | Grip corners or use channel/bar walls |
| half_moon | Distinguish the flat chord from the curved side |

No `V_PRONG`, no corner-aware placement, no tip clustering. Brief section 42
asked for classification rather than implementation here, and `EXPERIMENTAL`
with a per-shape recorded reason is that classification.

## Why `pearl` and `imported` are UNSUPPORTED

Both current families derive their geometry from a **planar girdle outline**.

- A **sphere has no girdle plane.** `stone_anchors()` returns an empty list and
  the registry's `anchors` field is empty to match. Real pearl settings (a
  cup-and-post, a half-drilled peg) are a different family, not a variation.
- **Imported geometry has no derived outline** yet. Projecting one from
  arbitrary imported geometry is the `STONE_OUTLINE_EXTRACTION` capability,
  status `PLANNED`. Reporting no outline is honest; fabricating one would place
  metal against a silhouette the stone does not have.

Both refuse with `SETTING_STONE_COMBINATION_UNSUPPORTED` — an explicit error,
never a silent substitution (SETTING-GOV-013).

## Compatibility is capability-based, not source-based

Brief section 74 asked that imported-stone setting support be decided from
geometry rather than granted. It is, and the same principle applies throughout:

- a **measured** stone uses its named shape's compatibility — the source mode
  does not change what a setting can grip;
- a **custom** stone is bezel-compatible because it carries a real outline, not
  because it is custom;
- an **imported** stone is refused because it carries no outline, not because it
  is imported.

If outline projection were implemented, imported stones would become compatible
without any change to this document's reasoning.
