# Stone v1 Migration

**There is no migration.** Every Stone v1 document keeps validating and keeps
generating identical geometry. That is the point of this document: to record
what makes that true, so a future change cannot quietly break it.

## What a Stone v1 document looks like

```json
{"shape": "round", "diameter": 6.5, "depth": 4.0}
{"shape": "oval", "length": 8.0, "width": 6.0, "depth": 4.0}
```

Neither sets `source`, `profile` or `narrowWidth`. Both still validate, because
all three are optional with defaults that reproduce pre-Sprint-20 behaviour
exactly:

```
source  = PARAMETRIC_REFERENCE
profile = FACETED_REFERENCE
narrowWidth = None
```

This is a MINOR, additive JDL change, on the same terms as Sprint 18's
(brief section 53).

## Round is byte-identical, and that is a geometry guarantee

A plain round faceted parametric stone takes `_build_round_stone()` — the exact
pre-Sprint-18 construction, untouched.

**The dispatch condition is deliberately narrow:**

```python
if (stone.shape == "round"
        and stone.source == "PARAMETRIC_REFERENCE"
        and stone.profile == "FACETED_REFERENCE"):
    return _build_round_stone(definition)
```

All three clauses are needed. A round CABOCHON or a round MEASURED stone must go
through the v2 pipeline; only the pre-existing case takes the pre-existing path.

**Why this is not merely a performance shortcut.** The two constructions produce
genuinely different geometry, measured:

| Path | Culet radius for a 6.5mm stone | Volume |
|---|---|---|
| `_build_round_stone` | 0.05mm (ABSOLUTE) | 58.2214 mm³ |
| shared pipeline | 0.1625mm (PROPORTIONAL) | 59.2820 mm³ |

A 1.8% difference. Routing round through the shared pipeline "for consistency"
would silently change every existing round model. Sprint 18 made the same choice
for the same reason.

Pinned by `test_round_geometry_differs_from_the_v2_pipeline`, so that if a
future refactor ever makes them identical, that becomes a deliberate decision
rather than a discovery in a Golden diff.

## The six non-round v1 shapes ARE routed through the v2 pipeline

...and are **bit-identical** doing so. Verified by running both implementations
on the same definition and requiring exact equality of volume and all six
bounding-box extents:

| Shape | v1 path | v2 path | Identical |
|---|---|---|---|
| oval | 67.34996594608987 | 67.34996594608987 | yes |
| pear | 52.05393726491256 | 52.05393726491256 | yes |
| emerald | 84.710745424 | 84.710745424 | yes |
| cushion | 84.89001462177934 | 84.89001462177934 | yes |
| princess | 85.75264000000003 | 85.75264000000003 | yes |
| marquise | 63.160827730166524 | 63.160827730166524 | yes |

The Sprint 18 implementation (`_build_non_round_stone`) is still present and is
what the test compares against — **no recorded constant to drift, and no
hand-written number to be wrong.**

An earlier version of that test *did* hardcode expected volumes, and five of the
six were subtly wrong: they had been typed rather than measured. That is exactly
what JDL-GOV-009 forbids, and it is why the test now compares implementations
instead of literals.

## Golden result

**Zero** Stone v1 baseline updates. All 23 pre-existing cases pass unchanged,
including the exact-equality guards:

```
combined metal volume  341.44334316909976
prong volume            29.650351464580467
round stone volume      58.22141924499569
```

## `definitionHash` drift — fourth consecutive occurrence

The additive `StoneSpec` fields changed `definition_hash()` for every document,
because `canonical_json()` serialises every field including new defaults.

Same mechanism as Sprints 17, 18 and 19. Still **not** a violation of JDL
Migration Requirement 4, which concerns migrating a stored document; this is
normalization-time default-filling on a fresh validation.

Verified again that `compare_snapshot()` never reads `definitionHash`, so Golden
regression is unaffected. Twelve stored fixtures were regenerated by **running
real code** — never hand-edited.

This is now a well-characterized structural tension rather than a surprise, and
is recorded once in
[`../appendices/jdl-version-compatibility-matrix.md`](../appendices/jdl-version-compatibility-matrix.md)
rather than re-derived each sprint. Resolving it (hash versioning, or excluding
defaults from the canonical form) needs an ADR.

## Tests that had to be retargeted

Three tests asserted that a now-real shape was unsupported. Each was retargeted
to `briolette` — genuinely reserved, with a real geometric reason — and each
gained a **complement** test:

| Test | Was | Now | Complement added |
|---|---|---|---|
| `test_unknown_shape_is_rejected` | asscher | briolette | every reserved shape is rejected |
| `test_unsupported_stone_shape_value_is_caught_deterministically` (Designer) | asscher | briolette | no Sprint 20 shape is reported unsupported |
| `test_unknown_family_or_shape_reports_unsupported` (Setting) | asscher | briolette | a pearl really is refused |

The Designer one has now been retargeted **twice** — Sprint 18 moved it from
`oval` to `asscher`. That recurrence is a feature of a healthy capability guard:
it fires precisely because the capability set genuinely grew. The complement
tests are what make each pair sound, because retargeting alone leaves nothing
guarding the other direction.
