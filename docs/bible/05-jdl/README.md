# Jewelry Definition Language v1 — Index

This is **Sprint 3** of the Technical Bible: **Jewelry Definition Language (JDL) v1**. It formalizes the stable boundary between design input, jewelry-domain concepts (Sprint 2), deterministic validation, geometry generation, preview, CAD export, and any future AI interpretation. It does not add a new ring style, a new geometry feature, AI-driven generation, authentication, payments, or any cloud service — see [`062-design-goals-and-non-goals.md`](062-design-goals-and-non-goals.md) for the explicit non-goal list.

**Read this README, then [`060-jdl-governance.md`](060-jdl-governance.md), before changing anything that touches `backend/jewelmind/domain/schema.py`, `shared/types/jewelry-definition.ts`, or `specs/jdl/v1/`.**

## The single most important fact in this section

JDL is a **language and semantic contract**, not one file format. It has three representations, at three different levels of reality:

| Representation | Status | Normative? |
|---|---|---|
| **Canonical JSON** | CURRENT — the only representation the running API accepts and produces today | **Yes — this is the only NORMATIVE representation** |
| **YAML serialization** | PLANNED — described in [`066-yaml-serialization-contract.md`](066-yaml-serialization-contract.md) for future implementers | No — non-normative |
| **Textual JDL DSL** | PLANNED — grammar drafted in [`specs/jdl/v1/jdl.ebnf`](../../../specs/jdl/v1/jdl.ebnf), no parser exists or is built in this milestone | No — non-normative |

The result of parsing and default-filling a Canonical JSON document is called the **JDL Canonical Document** everywhere in this section and in `specs/jdl/v1/`. Every other document in this Bible that needs to refer to "the normalized definition" should use this exact term.

## Front-matter field added this Sprint

```yaml
normative: true | false
```

- `true`: this document (or the representation/rule it describes) is binding — a deviation from it in code is a bug or requires an ADR.
- `false`: this document is informative/planned — it describes intent, a future contract, or background reasoning, and code cannot yet violate it because there is nothing running to violate.

This is independent of `implementation_status` and `professional_validation`: a document can be `implementation_status: planned` and still `normative: true` about the *rules that will govern* the planned feature once built (e.g. the YAML restriction list is normative-once-implemented, even though YAML support itself is planned).
