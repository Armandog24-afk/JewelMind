# Canonical JSON Serialization

This is the NORMATIVE serialization rule set for JDL v1. It describes exactly what `backend/jewelmind/utils/hashing.py::canonical_json()` does today — see [`specs/jdl/v1/canonicalization.md`](../../../specs/jdl/v1/canonicalization.md) for the terse machine-reference version and the exact algorithm.

| Rule | Behavior |
|---|---|
| Encoding | UTF-8 |
| Object model | A JSON object per `JDLDocumentV1` group (see [`064-canonical-document-model.md`](064-canonical-document-model.md)); no arrays exist in the current schema |
| Field naming | camelCase, exactly as declared in `backend/jewelmind/domain/schema.py` (e.g. `innerDiameter`, `prongCount`) — never renamed for serialization |
| Enum naming | snake_case string literals, exactly as declared (e.g. `comfort_fit`, `yellow_gold_18k`) |
| Numeric representation | Pydantic `float` fields always serialize with a decimal point (`16.0`, not `16`); `int` fields (`prongCount`) serialize without one |
| NaN / Infinity / -Infinity | Prohibited — impossible to construct a `JewelryDefinition` instance containing one, since every `float` field sets `allow_inf_nan=False` |
| Negative zero | Not specially handled by current code; no field's valid range currently produces `-0.0` in practice — documented gap, not a behavior change (see [`specs/jdl/v1/canonicalization.md`](../../../specs/jdl/v1/canonicalization.md)) |
| Null policy | No field in the current schema is nullable; `null` never appears in canonical output |
| Omitted vs. explicit default | Indistinguishable after canonicalization — proven by `minimal-solitaire.json` and `default-solitaire.json` sharing hash `355ddca57e7e49ad` |
| Key ordering | Alphabetical (`sort_keys=True`), recursively at every nesting level |
| Array-order semantics | Not exercised — no array-typed field exists today |
| Whitespace | None in canonical form (`separators=(",", ":")`); whitespace in the original authoring JSON has zero effect on the canonical form |
| Duplicate keys | Cannot survive JSON parsing (last-value-wins before Pydantic sees the data); no explicit rejection step exists in canonicalization itself |
| Relationship to the hash | `definition_hash()` = SHA-256 of the canonical JSON string, encoded UTF-8, truncated to the first 16 hex characters |
| Units | Millimeters implicitly, everywhere; no unit field, no conversion |

## Worked example

The default solitaire's canonical JSON (537 bytes, generated by running the real implementation):

```json
{"band":{"profile":"comfort_fit","thickness":1.8,"width":2.4},"jewelry":{"category":"ring","style":"solitaire"},"manufacturing":{"method":"lost_wax_casting"},"material":{"metal":"yellow_gold_18k"},"preview":{"angularTolerance":0.2,"meshTolerance":0.1},"project":{"name":"Solitaire Ring","units":"mm"},"ring":{"innerDiameter":17.8,"size":16.0,"sizeSystem":"EU"},"schemaVersion":"0.1.0","setting":{"basketHeight":3.5,"prongCount":6,"prongDiameter":1.1,"prongHeight":4.8,"type":"prong"},"stone":{"depth":4.0,"diameter":6.5,"shape":"round"}}
```

Hash: `355ddca57e7e49ad`. This exact string and hash are checked into `specs/jdl/v1/test-vectors/canonicalization-vectors.json` and `definition-hash-vectors.json`, and re-verified against a live run of `canonical_json()`/`definition_hash()` on every `pytest` invocation via `backend/tests/test_jdl_schema_examples.py`.

## Units decision

The canonical semantic unit system is **millimeters**, for every length field, with no exception and no unit field — this is unchanged from LAW-007 and is restated here because it is a JDL-level serialization fact, not only a domain fact.
