# JDL Governance

This document extends [`00-foundation/000-bible-governance.md`](../00-foundation/000-bible-governance.md)'s CURRENT/PARTIAL/PLANNED/VISION rule and [`04-jewelry-domain/040-domain-governance.md`](../04-jewelry-domain/040-domain-governance.md)'s classification model with rules specific to the Jewelry Definition Language: how a field, a representation, or a semantic rule is allowed to enter or change.

## JDL-GOV-001 through JDL-GOV-010

| ID | Rule |
|---|---|
| **JDL-GOV-001** | A field cannot be added only to the frontend. Every field in `shared/types/jewelry-definition.ts` must have a corresponding field in `backend/jewelmind/domain/schema.py`, and vice versa. The backend is always authoritative (see [`02-architecture/022-domain-boundaries.md`](../02-architecture/022-domain-boundaries.md)). |
| **JDL-GOV-002** | A schema change is either additive (new optional field with a default, new enum member appended) or a MAJOR version bump with a migration note — never a silent breaking change to `schemaVersion: "0.1.0"`. See [`081-schema-versioning-and-migrations.md`](081-schema-versioning-and-migrations.md). |
| **JDL-GOV-003** | Canonical JSON is the only NORMATIVE representation until a real parser for YAML or the textual DSL exists, is tested, and this document is updated to say so. No document may describe YAML or DSL input as currently accepted. |
| **JDL-GOV-004** | Structural (schema-layer) validation and semantic (business-rule) validation stay in separate artifacts: `specs/jdl/v1/jdl.schema.json` vs. `backend/jewelmind/validation/engine.py`. A schema-layer change must not silently absorb a semantic rule (or vice versa) without updating [`075-validation-pipeline.md`](075-validation-pipeline.md). |
| **JDL-GOV-005** | No jewelry measurement, tolerance, density, shrinkage value, or proportion may be introduced into a JDL document without a traceable source, per [`04-jewelry-domain/040-domain-governance.md`](../04-jewelry-domain/040-domain-governance.md) rule 2. This applies to JDL specification files exactly as it applies to Bible prose. |
| **JDL-GOV-006** | Unknown fields must not silently alter geometry. The current backend already enforces this structurally (`extra="forbid"` on every model in `backend/jewelmind/domain/schema.py`); the JSON Schema mirrors it (`additionalProperties: false` at every object level in `specs/jdl/v1/jdl.schema.json`). Any future extension mechanism must use an explicitly namespaced field (see [`082-extension-and-capability-model.md`](082-extension-and-capability-model.md)), never a bare unknown key. |
| **JDL-GOV-007** | A diagnostic code, once published in [`jdl-error-code-catalog.md`](../appendices/jdl-error-code-catalog.md), is never renamed or reused for a different meaning. It may be deprecated (see [`080-errors-warnings-and-diagnostics.md`](080-errors-warnings-and-diagnostics.md)). |
| **JDL-GOV-008** | Every claim in `specs/jdl/v1/` about current behavior must be backed by a test in `backend/tests/` or `frontend/src/**/*.test.ts`. A claim about planned behavior must be marked PLANNED and non-normative, per [`JM-BIBLE-JDL-README`](README.md)'s `normative` field. |
| **JDL-GOV-009** | Test vectors (`specs/jdl/v1/test-vectors/`) are generated by running the actual implementation. A hand-edited test vector that does not match a fresh run of `backend/tests/test_jdl_schema_examples.py` is a bug in the vector file, never treated as evidence the implementation is wrong. |
| **JDL-GOV-010** | The canonical document must produce reproducible geometry. For a fixed JDL Canonical Document and a fixed `GENERATOR_VERSION`, `build_solitaire_ring()` must yield the same component volumes, bounding boxes, and `definition_hash` on every run, on every machine — this is CLAUDE.md's "Preserve CAD determinism" rule, restated as a JDL-level contract in [`077-compiler-contract.md`](077-compiler-contract.md). |

## Relationship to the Constitution

JDL-GOV-010 operationalizes [LAW-003](../00-foundation/004-jewelmind-constitution.md#LAW-003) (deterministic geometry generation) specifically for the compiler contract. JDL-GOV-003 operationalizes [LAW-012](../00-foundation/004-jewelmind-constitution.md#LAW-012) (current vs. planned must stay distinct) for JDL representations specifically. JDL-GOV-005 has no direct Constitution LAW counterpart; it operationalizes [`04-jewelry-domain/040-domain-governance.md`](../04-jewelry-domain/040-domain-governance.md) rule 2 (no invented measurements) for language-level artifacts specifically.

## When an ADR or RFC is required for a JDL change

- **ADR required**: changing which JDL representation is normative; changing the coordinate/unit system; changing export defaults; moving validation authority between the structural and semantic layers; any change that violates JDL-GOV-001 through JDL-GOV-010 without superseding this document first.
- **RFC required** (per [`04-jewelry-domain/056-domain-extension-strategy.md`](../04-jewelry-domain/056-domain-extension-strategy.md)): adding a new ring style, stone shape, setting type, or jewelry category, even if expressed purely as new JDL enum members or fields.
- **Neither required**: adding a new document to this section, correcting a factual error against the current code, or filling in a previously-open question in [`086-open-jdl-questions.md`](086-open-jdl-questions.md) once a real decision has been made and recorded.
