# Stone v1 — Machine-Readable Specification

The machine-readable half of the Stone System. The narrative, architecture, and contract half lives in [`docs/bible/20-stone/`](../../../docs/bible/20-stone/README.md); start there for context.

## What the Stone System is

Stone System v1 (Sprint 18) generalizes the previously round-only `StoneReference` into **shared, category-neutral jewelry infrastructure** — it belongs to no single jewelry category (STONE-GOV-001; `jewelmind.geometry.stone` and `jewelmind.domain.stone_dimensions` never import `jewelmind.ring`, enforced by `backend/tests/test_stone_system_no_ring_dependency.py`). All 7 target shapes generate real, deterministic CAD reference geometry: `round`, `oval`, `pear`, `emerald`, `cushion`, `princess`, `marquise`.

A `StoneReference` is deterministic geometric reference suitable for CAD construction, layout, setting construction, clearance analysis, Vision, and technical communication. It is **never** a claim of exact facet pattern, optical behavior, commercial cutting proportions, gemological certification, or vendor dimensions (STONE-GOV-011). A richer `FACETED_GEM_MODEL` layer is a future, separate concern — see [`docs/bible/20-stone/567-stone-reference-geometry-contract.md`](../../../docs/bible/20-stone/567-stone-reference-geometry-contract.md).

## Files

| File | Purpose |
|---|---|
| [`stone-definition.schema.json`](stone-definition.schema.json) | The full real contract: the JDL-facing `stone` input plus the `generatedMetadata` a real `build_stone()` call returns |
| [`stone-dimensions.schema.json`](stone-dimensions.schema.json) | The resolved LENGTH/WIDTH/DEPTH contract every module consumes (round normalizes to `length == width == diameter`) |
| [`stone-orientation.schema.json`](stone-orientation.schema.json) | The `stone.orientation` rotation contract, in the stone's own placement frame |
| [`stone-shape-capability.schema.json`](stone-shape-capability.schema.json) | One shape's capability entry — including the deliberate split between generation capability and Setting compatibility |
| [`stone-reference-profile.schema.json`](stone-reference-profile.schema.json) | The fixed software construction parameters (crown/pavilion/table ratios, corner ratios), all `provenance: software_reference_profile` |
| [`shape-registry.json`](shape-registry.json) | Every shape's real capability entry — generated from `geometry/stone/capability.py`, the real source of truth (STONE-GOV-014) |

## Examples

7 examples in [`examples/`](examples/), one per shape, each a real `{stone, generatedMetadata, volumeMm3, boundingBox}` produced by actually calling `build_stone()`: `round.json`, `oval.json`, `pear.json`, `emerald.json`, `cushion.json`, `princess.json`, `marquise.json`.

## Test vectors

5 files in [`test-vectors/`](test-vectors/): `shape-normalization-vectors.json` (the real Designer IT/EN synonym table), `dimension-vectors.json` (real `resolved_length_mm()`/`resolved_width_mm()`/`resolved_depth_mm()` output per shape), `orientation-vectors.json` (real bounding boxes and volumes at 0°/90°/180° for `oval`/`pear`/`marquise`), `invalid-stone-vectors.json` (real `StoneSpec` validation failures), and `backward-compatibility-vectors.json` (a pre-Sprint-18 round document still validating and producing the byte-identical pre-Sprint-18 volume).

## Setting compatibility is NOT stone-generation capability

Every non-round shape's `currentSettingCompatibility` is `EXPERIMENTAL`, deliberately (STONE-GOV-009, brief section 27): the current prong layout is a **generic, provisional circular placement**, not shape-optimized. A shape generating real geometry is never a claim that its prong setting is professionally valid. Only `round` is `SUPPORTED`.

## No fabricated measurements, and no fake equivalent diameter

Every example, test-vector, and the shape registry were generated by actually running the real `geometry.stone.builder.build_stone()` / `domain.stone_dimensions` / `geometry.stone.capability` code (via a one-off `backend/generate_stone_specs.py`, run once and not part of the shipped code or test suite) — never hand-typed. `backend/tests/test_stone_schemas.py` re-validates all of it.

No `length × width` is ever collapsed into a synthetic "equivalent diameter" for rule compatibility (brief section 44). Round-only Forge rules (`JM-STONE-001`, `JM-PRONG-003`) are explicitly scoped to `shape == "round"`; `JM-STONE-002` was genuinely generalized to the stone's real minimum horizontal extent. See [`docs/bible/20-stone/578-current-code-mapping-and-gaps.md`](../../../docs/bible/20-stone/578-current-code-mapping-and-gaps.md).

## How these files are validated

`backend/tests/test_stone_schemas.py` validates all 5 schemas, all 7 examples, and every test-vector file using the same `jsonschema` library used for every prior sprint's specs, plus re-derives examples live to catch pipeline drift.
