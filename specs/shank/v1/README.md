# Shank v1 — Machine-Readable Specification

The machine-readable half of the Band & Shank System. The narrative, architecture, and contract half lives in [`docs/bible/19-shank/`](../../../docs/bible/19-shank/README.md); start there for context.

## What Shank is

Shank is the internal technical name (SHANK-GOV-001) for the reusable, parametric ring-band geometry subsystem introduced in Sprint 17, replacing the previous single-file uniform-only implementation. The JDL-facing field stays `band` (unchanged, backward-compatible — see [`556-current-band-migration.md`](../../../docs/bible/19-shank/556-current-band-migration.md)); "Shank" never appears in user-facing product copy (SHANK-GOV-002, mirroring STUDIO-GOV-011). v1 supports a uniform shank (byte-identical to the pre-Sprint-17 construction) and a real, deterministic linear width and/or thickness taper anchored at the head. Split shank, cathedral, knife edge, Euro shank, twisted, sculptural, and multi-rail shanks are architecturally reserved names only — see [`capability-registry.json`](capability-registry.json) — and are not implemented.

## Files

| File | Purpose |
|---|---|
| [`shank-definition.schema.json`](shank-definition.schema.json) | The full real contract: the JDL-facing `band` input plus the `generatedMetadata` a real `build_shank()` call returns, split into `UniformShankMetadata`/`TaperedShankMetadata` |
| [`section-profile.schema.json`](section-profile.schema.json) | One cross-section (`flat` or `comfort_fit`) at a given angular position |
| [`width-function.schema.json`](width-function.schema.json) | One sample of the deterministic width function w(u) |
| [`thickness-function.schema.json`](thickness-function.schema.json) | One sample of the deterministic thickness function t(u) |
| [`taper-definition.schema.json`](taper-definition.schema.json) | Mirrors `BandTaperSpec` exactly — also the real JDL `band.widthTaper`/`band.thicknessTaper` shape |
| [`connection-interface.schema.json`](connection-interface.schema.json) | Mirrors `ShankConnectionInterface` exactly — the explicit Shank → RingHead handoff |
| [`capability-registry.json`](capability-registry.json) | Every named Shank capability, `current` vs `planned`, and its `jdlExposed`/`generatable`/`inspectable` status — generated from `geometry/shank/capability.py`, the real source of truth |

## Examples

5 examples in [`examples/`](examples/), each a real `{band, generatedMetadata, volumeMm3, boundingBox}` produced by actually calling `build_shank()`: `uniform-comfort-fit.json` (the default), `uniform-flat.json`, `tapered-width.json` (60% at the bottom), `tapered-thickness.json` (50% at the bottom), `combined-taper.json` (flat profile, both tapers).

## Test vectors

6 files in [`test-vectors/`](test-vectors/): `profile-vectors.json`, `width-function-vectors.json`, `thickness-function-vectors.json`, `taper-vectors.json` (real `taper_ratio()`/`angle_deg_for_u()` outputs across `u ∈ {0, 0.25, 0.5, 0.75, 0.99}`), `compatibility-vectors.json` (proves a no-taper request produces `variation: "UNIFORM"`, `sectionCount: 1` — the old construction path), `invalid-shank-vectors.json` (real `BandTaperSpec` validation failures).

## No fabricated measurements

Every example, test-vector, and the capability registry were generated by actually running the real `geometry.shank.builder.build_shank()`/`geometry.shank.taper` code and the real `geometry.shank.capability.SHANK_CAPABILITIES` registry (via a one-off `backend/generate_shank_specs.py`, run once and not part of the shipped code or test suite) — never hand-typed. `backend/tests/test_shank_schemas.py` re-validates all of it.

## How these files are validated

`backend/tests/test_shank_schemas.py` validates all 6 schemas and all 5 examples using the same `jsonschema` library used for every prior sprint's specs, plus re-derives one example live to catch pipeline drift.
