# Ring Family v1 — machine-readable specification

The machine half of [`docs/bible/30-ring-families/`](../../../docs/bible/30-ring-families/README.md)
(Sprint 28). Every file here is **generated by running the real
implementation** and is re-derived by
`backend/tests/test_ring_families.py::TestSpecArtifacts` on every test run, so
a drift between this directory and the code **fails** rather than survives.

Sprint 20 deleted three hand-copied registries that had already drifted and had
caused Designer and the Setting System to misreport real capabilities. Nothing
here is hand-authored (JDL-GOV-009).

## What a ring family is

A **parametric relation**, not a preset. A family derives the blocks it owns —
the band's architecture, the head's height, the side stones, the halo, the pavé
— from a small set of family parameters and from the document's own values. So
changing `ring.innerDiameter`, `stone.diameter` or `band.width` regenerates the
design rather than leaving a stored model stale.

Two fields express it, and both are flat scalars:

| Field | Meaning |
| --- | --- |
| `jewelry.style` | the **family** (`solitaire`, `three_stone`, `halo`, `split_shank`, `bypass`, `signet`) |
| `ringFamily.variant` | which **variant** of that family |

`jewelry.style` has meant "ring family" since Sprint 16, so Sprint 28 extended
it rather than adding a second field that could disagree with it. A variant
belonging to another family is **refused** (`JM-RINGFAM-001`), never resolved by
precedence — the discipline `JM-FAMILY-001` and `JM-SETTING-008` already carry.

`ringFamily: null` means "no variant declared". For `solitaire` that resolves to
`SOLITAIRE_CLASSIC`, which reproduces the pre-Sprint-28 design exactly.

### Registry

`ring-family-registry.json` — the 6 families, the 13 variants, the 9 reserved
names with their real technical reasons, the 40 designer terms, and which
parameters each variant reads.

Its central axis is **measured, not declared**:
`differsFromFamilyBaseline` and `derivedPathCount` come from running the real
resolver against a real default document. Exactly one variant may report
`differsFromFamilyBaseline: false` — `SOLITAIRE_CLASSIC`, which IS the baseline
the others differ from, and which is the one flagged `isFamilyBaseline: true`.
A variant that stopped deriving anything would report it on the next import.

`structuralGeometry` is **declared**, and that is a boundary rather than a gap:
measuring it needs the live builder registries in `jewelmind.geometry`, and the
ring-family layer is carried in JDL and read by Forge, so it must not reach into
geometry. `pave/capability.py` settles the same tension the same way, and
`test_ring_families.py::test_declared_structural_geometry_matches_the_builders`
asserts the correspondence in both directions.

### Dependency graph

`ring-family-dependency-graph.json` — every JDL path a variant **derives**, and
every document field that **influences** what it derives (`ring.size`,
`band.thickness`, `band.width`, `stone.diameter`). This is the parametric claim
as inspectable data, and the resolver self-checks each write against it at
runtime: a path written but not declared raises.

### Examples

Seven real documents, one per structurally distinct capability, each recorded
with the resolution the real resolver produces for it. Every example is a design
`validate_definition()` accepts with no errors.

### Test vectors

| File | What it records |
| --- | --- |
| `ring-family-fingerprint-vectors.json` | `ring_family_fingerprint()` output — 16 hex characters, deterministic, no timestamp/randomness/pid/memory |
| `ring-family-derivation-vectors.json` | every derivation each variant makes, with the source parameters it was computed from |
| `ring-family-geometry-vectors.json` | **measured** volumes, solid counts and component sets from real generated solids |
| `ring-family-compatibility-vectors.json` | the one number that must not move: the pre-Sprint-28 solitaire at `341.44334316909976 mm³` |

The geometry vectors are re-measured by rebuilding each variant, because a spec
whose geometry figures were typed by hand could claim any difference between two
variants.

## What is NOT here

**No professional threshold, and no claim of one.** Nothing in this directory
states how thin a rail may be, whether a shoulder is castable, whether a signet
table is thick enough, or whether a bypass would hold. Each needs sourced
professional evidence this project does not have.

The two numeric limits that do exist are **arithmetic**, and each says so:

- `JM-RINGFAM-004` refuses a rail separation that leaves *no rail* — the rails
  share the band's width, so `(width − separation) / 2` is what is left. That is
  subtraction, not a judgment about thinness.
- `geometry/shoulder.py::MAX_ARCH_SPAN_DEG = 90.0` is the measured limit of a
  ruled-loft arch: the base section's rotation is `−90 + span`, so past 90° it
  has rotated beyond the head's own section and the loft turns back on itself.
  Found by measuring — at 90° the arches are 84.651 mm³ and the ring's metal is
  valid; at 92° they collapse to 19.577 mm³ and the combined metal is invalid.

**Every variant is `NOT_REVIEWED`.** Two families are honestly `PARTIAL`:

- `halo` — the halo stones are real geometry, and **no metal is generated to
  hold them**. Sprint 25's own recorded boundary, unchanged here.
- `signet` — the body and its table are real geometry, and the table is flat and
  rectangular: **no engraving, relief or texture exists anywhere in the
  pipeline**. `SIGNET_ENGRAVED` and `SIGNET_OVAL_TABLE` are reserved with their
  real reasons.

## Regenerating

These files are regenerated by running the real implementation, never edited by
hand. `TestSpecArtifacts` is what tells you a regeneration is due.
