# JDL v1 — Machine-Readable Specification

This directory is the machine-readable half of the JewelMind Jewelry Definition Language (JDL) v1 specification. The narrative, rationale, and governance half lives in [`docs/bible/05-jdl/`](../../../docs/bible/05-jdl/README.md); start there for context. This README only indexes what's in this directory and states which files are normative.

## Normative representation

**Canonical JSON is the only NORMATIVE JDL representation today.** It is the only one the running application (`backend/jewelmind/domain/schema.py` via FastAPI/Pydantic) actually accepts and produces. The result of parsing and defaulting a Canonical JSON document is called the **JDL Canonical Document** throughout this specification.

YAML serialization and the textual JDL DSL described in this directory are **PLANNED and NON-NORMATIVE**. No parser exists for either today, and none is built as part of this milestone. Do not treat any file in this directory as evidence that YAML or textual-DSL input is currently accepted by the API — it is not.

## Files

| File | Status | Purpose |
|---|---|---|
| [`jdl.schema.json`](jdl.schema.json) | NORMATIVE (structural layer only) | JSON Schema (2020-12) for a JDL v1 Canonical Document. Deliberately omits jewelry business-rule thresholds enforced only at the semantic-validation layer — see the schema's own `description` fields. |
| [`jdl.ebnf`](jdl.ebnf) | PLANNED, NON-NORMATIVE | Grammar only for the future textual DSL. No parser exists or is planned for this milestone. |
| [`canonicalization.md`](canonicalization.md) | NORMATIVE | Exact canonicalization/hashing algorithm, as implemented today in `backend/jewelmind/utils/hashing.py`. |
| [`compiler-contract.md`](compiler-contract.md) | NORMATIVE (CURRENT rows) / informative (PARTIAL rows) | Maps the conceptual `CompilationResult` onto the current backend's actual types and call sequence. |
| [`examples/`](examples/) | NORMATIVE (valid Canonical JSON) | 7 example documents, all generated from and verified against the real running backend. |
| [`examples/invalid/`](examples/invalid/) | NORMATIVE (as counter-examples) | 5 example documents that are each invalid for one specific, documented reason. See [`docs/bible/appendices/jdl-example-index.md`](../../../docs/bible/appendices/jdl-example-index.md) for which layer (structural schema vs. semantic validation) rejects each one. |
| [`test-vectors/`](test-vectors/) | NORMATIVE | Canonicalization, definition-hash, validation, and schema-version-compatibility vectors, all generated by running the actual current implementation — never hand-invented. |

## How these files are validated

`backend/tests/test_jdl_schema_examples.py` (added in Sprint 3) runs on every `pytest` invocation and:

1. Validates every file in `examples/` against `jdl.schema.json` and asserts zero schema errors.
2. Constructs a `JewelryDefinition` from every file in `examples/` and asserts it succeeds, then re-runs `validate_definition()` and asserts zero `error`-severity results.
3. For each file in `examples/invalid/`, asserts it fails at the documented layer (Pydantic construction, or `validate_definition()` producing at least one `error`-severity result with the documented rule ID).
4. Recomputes `canonical_json()` / `definition_hash()` for every parseable example and compares against `test-vectors/canonicalization-vectors.json` / `test-vectors/definition-hash-vectors.json`.

This keeps the specification honest against the real implementation on every CI run, rather than only at the moment this Sprint was written.
