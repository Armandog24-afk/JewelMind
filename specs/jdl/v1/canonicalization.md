# JDL v1 Canonicalization — Machine Reference

Normative narrative: [`docs/bible/05-jdl/076-canonicalization-and-definition-hashing.md`](../../../docs/bible/05-jdl/076-canonicalization-and-definition-hashing.md).
This file is the terse, implementation-facing companion for tool authors.

## Algorithm (exact, as implemented in `backend/jewelmind/utils/hashing.py`)

```
canonical_json(definition) = json.dumps(
    definition.model_dump(mode="json"),
    sort_keys=True,
    separators=(",", ":"),
)

definition_hash(definition) = sha256(canonical_json(definition).encode("utf-8")).hexdigest()[:16]
```

## Rules

1. **Input to canonicalization is a validated `JewelryDefinition` instance**, never raw untrusted JSON text. A document that fails Pydantic construction (wrong `schemaVersion`, wrong type, non-finite number where `allow_inf_nan=False` applies, unknown field) never reaches this step and has no canonical form or hash.
2. **All fields participate**, including `preview.meshTolerance` and `preview.angularTolerance`. There is currently no field exclusion list. Whether preview parameters *should* participate in the hash is open question JDL-OQ-001 (see [`086-open-jdl-questions.md`](../../../docs/bible/05-jdl/086-open-jdl-questions.md)) — today's behavior includes them, full stop.
3. **Key ordering**: alphabetical (`sort_keys=True`), applied recursively at every nesting level, including nested object keys. Array order is not exercised by the current schema (no array-typed fields exist in `JewelryDefinition` today).
4. **Whitespace**: none — `separators=(",", ":")` produces the minimal-whitespace form. Whitespace in the *authoring* representation (however a document reaches the API) has no effect on the canonical form or the hash.
5. **Numeric representation**: values pass through Python's `json.dumps` after Pydantic's `model_dump(mode="json")`. A `float` field always serializes with a decimal point (e.g. `size: 16` becomes `16.0` in canonical form), because `RingSpec.size` is typed `float` in the schema regardless of the literal used at the call site. An `int` field (`setting.prongCount`) serializes without a decimal point.
6. **NaN / Infinity / -Infinity**: excluded by construction — every plain `float` field in `JewelryDefinition` sets `allow_inf_nan=False`, so a `JewelryDefinition` instance can never hold a non-finite value in the first place. Canonicalization itself performs no additional non-finite check because it never needs to.
7. **Negative zero**: not specially handled; Python's `json.dumps(-0.0)` emits `-0.0`. No current field's valid range makes `-0.0` a meaningful input, so this has not been exercised or fixed — flagged as a documentation gap, not a behavior change, in the Sprint 3 validation report.
8. **Omitted vs. explicit default**: indistinguishable after canonicalization. An omitted field and one explicitly set to its default value produce byte-identical canonical JSON (proved by `test-vectors/definition-hash-vectors.json`: `minimal-solitaire.json` and `default-solitaire.json` share hash `355ddca57e7e49ad`).
9. **`schemaVersion` is included** in the hash. A future `0.2.0` document with otherwise-identical field values will hash differently from an equivalent `0.1.0` document, by design — the hash identifies a definition *under a specific schema version*, not a value tuple independent of version.
10. **No timestamp participates.** Nothing in `JewelryDefinition` is a generation timestamp; `ModelRecord.generated_at` (assigned when a model is generated) lives outside the definition and is never part of `canonical_json()`.
11. **Units are implicit millimeters** everywhere; there is no unit field to normalize or strip.
12. **Duplicate keys**: cannot occur in a parsed Python object (JSON parsing collapses duplicate keys to the last-seen value before Pydantic ever sees the data); canonicalization does not need to detect or reject them itself. A textual-DSL parser (once built) would need its own duplicate-key policy — see [`068-lexical-conventions.md`](../../../docs/bible/05-jdl/068-lexical-conventions.md).
13. **Stability**: for a fixed `JewelryDefinition` field-value tuple and a fixed generator/library version, `canonical_json()` and `definition_hash()` are deterministic and reproducible — verified directly in `test-vectors/definition-hash-vectors.json` and `test-vectors/canonicalization-vectors.json`, both generated by running this exact code, not invented by hand.

## Known limitation

Canonicalization is defined over a Python object graph, not over raw JSON text. A raw JSON document containing the non-standard tokens `Infinity`, `-Infinity`, or `NaN` (which Python's `json` module accepts as an extension, even though standard JSON forbids them) will fail Pydantic construction — see `examples/invalid/invalid-non-finite-number.json` — and therefore never reaches this canonicalization step. This is enforced by Pydantic (`allow_inf_nan=False`), not by JSON Schema, which has no native way to express "finite number" (see `jdl.schema.json`'s description field and [`083-security-and-resource-limits.md`](../../../docs/bible/05-jdl/083-security-and-resource-limits.md)).
