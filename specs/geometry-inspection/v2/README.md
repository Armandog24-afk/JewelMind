# Geometry Inspection v2 — Machine-Readable Specification

The machine-readable half of the Geometry Inspection Framework. The narrative, architecture, and contract half lives in [`docs/bible/16-geometry-inspection/`](../../../docs/bible/16-geometry-inspection/README.md); start there for context.

## What Geometry Inspection is

Geometry Inspection v2 is Atlas's real, runtime fact-gathering subsystem: it reports what a generated model's geometry actually *is* (component counts, volumes, bounding boxes, solid counts, pairwise intersections/distances, connectivity groups, StoneReference separation, requested-vs-generated prong count) — never what it *means* professionally or for manufacturing. Every schema here describes the real, currently-implemented pipeline in `backend/jewelmind/geometry/inspection/`.

## Files

| File | Purpose |
|---|---|
| [`geometric-fact.schema.json`](geometric-fact.schema.json) | One kernel-neutral geometric fact — the flattened, Forge-consumable representation |
| [`component-inspection.schema.json`](component-inspection.schema.json) | Runtime inspection of one named component |
| [`assembly-inspection.schema.json`](assembly-inspection.schema.json) | Assembly-level facts — inlines connectivity/intersection/distance/stone-separation/prong-count shapes, matching every prior sprint's convention of not using cross-file `$ref` |
| [`connectivity-result.schema.json`](connectivity-result.schema.json) | A real connectivity graph (PRODUCTION or FULL_ASSEMBLY) |
| [`intersection-result.schema.json`](intersection-result.schema.json) | One pairwise intersection result |
| [`distance-result.schema.json`](distance-result.schema.json) | One pairwise minimum-distance result |
| [`inspection-report.schema.json`](inspection-report.schema.json) | The complete `GeometryInspectionReport` — the response body of `GET /api/models/{modelId}/inspection` |
| [`inspection-diagnostic.schema.json`](inspection-diagnostic.schema.json) | One of the 11 `INSPECTION_*` diagnostic codes |
| [`inspection-version.schema.json`](inspection-version.schema.json) | How a change to inspection semantics is classified (PATCH/MINOR/MAJOR) |
| [`fact-registry.json`](fact-registry.json) | A hand-authored catalog of all 16 `FactType` values — semantic meaning, value type, unit, scope, implementation status, and Forge-consumption status. No professional thresholds appear anywhere in this file. |

## Examples

5 examples in [`examples/`](examples/), each a real `GeometryInspectionReport` (or a focused excerpt) produced by actually inspecting real generated geometry: `default-solitaire-inspection.json` (the default 6-prong solitaire), `four-prong-inspection.json`, `disconnected-component-example.json` (a TEST-FIXTURE-ONLY set of plain cubes, never a supported jewelry model — demonstrates a real `DISCONNECTED` connectivity result), `stone-separation-example.json`, and `failed-inspection-example.json` (a component deliberately emptied to exercise the `FAIL`/`INSPECTION_COMPONENT_MISSING` path).

## Test vectors

8 files in [`test-vectors/`](test-vectors/): `component-presence-vectors.json`, `solid-count-vectors.json`, `connectivity-vectors.json`, `intersection-vectors.json`, `distance-vectors.json`, `stone-separation-vectors.json`, `determinism-vectors.json` (two independent inspection runs of the identical geometry, proving equivalent facts), and `regression-vectors.json` (a real baseline for the default solitaire, to be compared with tolerance, never exact floating-point equality).

## No fabricated measurements

Every example and test-vector file was generated by actually running the real `jewelmind.geometry.inspection.inspect_model()` pipeline (via a one-off `backend/generate_inspection_specs.py`, run once and not part of the shipped code or test suite) against real generated solitaire geometry — never hand-typed. `backend/tests/test_geometry_inspection_schemas.py` re-validates all of it.

## How these files are validated

`backend/tests/test_geometry_inspection_schemas.py` validates all 9 schemas and all 5 examples using the same `jsonschema` library used for every prior sprint's specs, plus re-derives the default-solitaire example live to catch pipeline drift.
