# Professional Validation v1 — Machine-Readable Specification

The machine-readable half of the Professional Validation Framework. The narrative, architecture, and contract half lives in [`docs/bible/15-professional-validation/`](../../../docs/bible/15-professional-validation/README.md); start there for context.

## What Professional Validation is

This framework never performs professional validation itself. It is the infrastructure that lets a real, identifiable jewelry professional's review of JewelMind's geometry, Forge rules, and manufacturing-context assumptions be captured as structured, versioned, auditable evidence — see `backend/jewelmind/professional_validation/`. As of this Sprint, **the active registry contains zero validated entries**, because no real professional review has occurred.

## Files

| File | Purpose |
|---|---|
| [`reviewer.schema.json`](reviewer.schema.json) | A real, named reviewer's minimal identity record |
| [`reviewer-qualification.schema.json`](reviewer-qualification.schema.json) | A reviewer's fit-for-review profile — never a prestige score |
| [`validation-scope.schema.json`](validation-scope.schema.json) | What a validation decision actually covers, never broader than the evidence |
| [`review-session.schema.json`](review-session.schema.json) | One real sitting with one reviewer |
| [`review-case.schema.json`](review-case.schema.json) | A reproducible review unit — same JDL, same pinned versions, same result |
| [`review-observation.schema.json`](review-observation.schema.json) | One reviewer note — never itself a validation decision |
| [`validation-decision.schema.json`](validation-decision.schema.json) | One reviewer's decision about one exact statement |
| [`validation-evidence.schema.json`](validation-evidence.schema.json) | One piece of evidence, with a qualitative (never numeric) quality class |
| [`validation-record.schema.json`](validation-record.schema.json) | The one artifact that can ever claim professional validation occurred |
| [`review-package-manifest.schema.json`](review-package-manifest.schema.json) | The manifest bundled inside every generated Professional Review Package |
| [`current-validation-registry.json`](current-validation-registry.json) | The single active registry — **zero records**, by design, until real review occurs |
| [`examples/`](examples/) | 4 single-record examples (2 empty templates, 1 conditional, 1 rejected) + 1 two-record conflicting-review example — every one marked `isTemplate: true` |
| [`test-vectors/`](test-vectors/) | 6 test-vector files: status transitions, scope matching, qualification-to-review-area mapping, version-impact classification, disagreement preservation, revalidation triggers |

## The one hard rule every file here follows

**A `ValidationRecord` with `isTemplate: true` must never appear in `current-validation-registry.json`.** This is enforced twice: structurally (examples live in a separate directory the registry loader never reads) and defensively (`backend/jewelmind/professional_validation/registry.py::load_active_registry()` raises if it ever finds `isTemplate: true` in the registry file it did load). `backend/tests/test_professional_validation_registry.py` and `test_professional_validation_specs.py` both verify this live.

## No fabricated examples

Every example and test-vector file was generated by actually constructing and validating the real `ValidationRecord`/`ValidationScope`/`DisagreementRecord` Pydantic models and running the real `scope_matches()` function (via a one-off `backend/generate_professional_validation_specs.py`, run once and not part of the shipped code or test suite) — never hand-typed JSON that could silently drift from the schema. `backend/tests/test_professional_validation_specs.py` re-validates all of it, including reproducing every `scope-vectors.json` entry live against `scope_matches()`.

## How these files are validated

`backend/tests/test_professional_validation_specs.py` validates all 10 schemas, all 5 example files (including the two-record conflicting-review example), all 6 test-vector files, and the active registry's continued emptiness, using the same `jsonschema` library used for every prior sprint's specs.
