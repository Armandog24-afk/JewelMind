# Design Intent v1 — Machine-Readable Specification

The machine-readable half of the Design Intent Model. The narrative, architecture, and contract half lives in [`docs/bible/13-design-intent/`](../../../docs/bible/13-design-intent/README.md); start there for context.

## What Design Intent is

Design Intent is the formal semantic layer between natural aesthetic language ("delicate", "minimal", "classic") and JewelMind's deterministic `JewelryDefinition`. Every schema here describes the real, currently-implemented pipeline in `backend/jewelmind/design_intent/` — subjective language is structured, preserved, and reviewable, but never silently converted into a numeric dimension.

## Files

| File | Purpose |
|---|---|
| [`intent-target.schema.json`](intent-target.schema.json) | The 10 canonical targets a statement/relation can be about |
| [`intent-statement.schema.json`](intent-statement.schema.json) | One structured aesthetic descriptor |
| [`intent-relation.schema.json`](intent-relation.schema.json) | One relative proportional relationship between two targets |
| [`intent-diagnostic.schema.json`](intent-diagnostic.schema.json) | One diagnostic entry (the 9 `INTENT_*` codes) |
| [`intent-resolution.schema.json`](intent-resolution.schema.json) | A record of how one statement was, or wasn't, resolved (not currently persisted) |
| [`intent-profile.schema.json`](intent-profile.schema.json) | A future, versioned, deterministic intent-to-JDL mapping (no profile is registered in v1) |
| [`design-intent.schema.json`](design-intent.schema.json) | The full `DesignIntent` document — inlines the shapes above, matching every prior sprint's convention of not using cross-file `$ref` |
| [`vocabulary.json`](vocabulary.json) | The controlled vocabulary source of truth: 6 concept categories, each an ordered continuum, plus their real IT/EN synonym tables, target synonyms, and relation predicates — **no CAD/numeric mapping appears anywhere in this file** |
| [`examples/`](examples/) | 7 examples — a delicate solitaire, a bold one, a minimal/classic one, a relation-only one, a conflicting-intent one, an unresolved-descriptor one, and a MODIFY (before/after) one |
| [`test-vectors/`](test-vectors/) | 6 test-vector files: descriptor normalization, target resolution, conflict detection, preservation across MODIFY, intent diffing, and deterministic resolution (proving every v1 statement resolves to `PRESERVED`, never a numeric mapping) |

## No fabricated examples

Every example, test-vector, and the vocabulary file itself were generated by actually running `jewelmind.design_intent.resolver.build_design_intent()` and the real vocabulary module (via a one-off `backend/generate_design_intent_specs.py`, run once and not part of the shipped code or test suite) — never hand-typed. `backend/tests/test_design_intent_schemas.py` re-validates all of it.

## Zero automatic numeric mappings — verified, not just claimed

[`deterministic-resolution-vectors.json`](test-vectors/deterministic-resolution-vectors.json) is generated directly from the real pipeline and shows every recognized statement resolving to `resolutionStatus: PRESERVED` — never `DETERMINISTICALLY_RESOLVED`. See [`docs/bible/13-design-intent/349-deterministic-resolution-policy.md`](../../../docs/bible/13-design-intent/349-deterministic-resolution-policy.md) for why this is the deliberately correct v1 state, not an unfinished feature.

## How these files are validated

`backend/tests/test_design_intent_schemas.py` validates all 7 schemas and all 7 examples using the same `jsonschema` library used for every prior sprint's specs, plus re-derives the MODIFY example live to catch pipeline drift.
