# Designer v1 — Machine-Readable Specification

The machine-readable half of Designer. The narrative, architecture, and contract half lives in [`docs/bible/12-designer/`](../../../docs/bible/12-designer/README.md); start there for context.

## What Designer is

Designer turns a natural-language jewelry design request (Italian or English) into a structured, reviewable `DesignerProposal` — never geometry, never a bypass of JDL/Forge validation, never a claim of manufacturability. Every schema here describes the real, currently-implemented pipeline in `backend/jewelmind/designer/`, not a target architecture.

## Files

| File | Purpose |
|---|---|
| [`natural-language-request.schema.json`](natural-language-request.schema.json) | The body of `POST /api/designer/interpret` |
| [`proposed-field.schema.json`](proposed-field.schema.json) | One field, with mandatory provenance + confidence |
| [`clarification-question.schema.json`](clarification-question.schema.json) | A structured, constrained-choice clarification question |
| [`unsupported-feature.schema.json`](unsupported-feature.schema.json) | A requested feature JewelMind cannot currently produce |
| [`designer-diagnostic.schema.json`](designer-diagnostic.schema.json) | One diagnostic entry (the 5 non-fatal `DESIGNER_*` codes) |
| [`design-proposal.schema.json`](design-proposal.schema.json) | The full proposal — inlines the four shapes above, matching every prior sprint's convention of not using cross-file `$ref` |
| [`designer-result.schema.json`](designer-result.schema.json) | The full `POST /api/designer/interpret` response body |
| [`examples/`](examples/) | 6 examples — minimal supported, complete multi-field, ambiguous, vague/unresolved, unsupported (halo), and mixed supported/unsupported |
| [`test-vectors/`](test-vectors/) | 7 test-vector files: intent mapping, defaulting, ambiguity, clarification, unsupported-feature detection, proposal-to-JDL, and field provenance |

## No fabricated examples

Every example and test-vector file was generated by actually running `DesignerService` with `FakeDesignerProvider` against real `RawDesignerResponse` fixtures (see the one-off `backend/generate_designer_specs.py`, run once and not part of the shipped code or test suite) — never hand-typed. `backend/tests/test_designer_schemas.py` re-derives two of them live to catch drift.

## What is, and isn't, live-verified here

Every example was produced by the real deterministic pipeline (normalization, capability checking, provenance/confidence tagging, candidate JDL construction, Forge evaluation, diffing) — that part is fully exercised and tested. No example was produced by an actual LLM call: this development environment has no configured AI provider credential, so `AnthropicDesignerProvider` (backend/jewelmind/designer/provider.py) is implemented but not live-verified — see [`docs/bible/12-designer/SPRINT-10-VALIDATION-REPORT.md`](../../../docs/bible/12-designer/SPRINT-10-VALIDATION-REPORT.md).

## How these files are validated

`backend/tests/test_designer_schemas.py` validates all 7 schemas and all 6 examples using the same `jsonschema` library used for every prior sprint's specs.
